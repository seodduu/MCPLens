# How It Works

이 문서를 끝내면 MCP Lens가 보여주는 모든 숫자 뒤에 있는 세 가지 움직이는 부품을 이해한 상태가
된다. 비용을 재는 정의 스캔, 호출을 재는 훅 기반 사용량 수집, 그리고 이 둘을 시간이 지나도
정확하게 유지하는 스냅샷 저장이다. 명령어 자체는 [Quick Start](/ko/quick-start)와
[CLI reference](/ko/reference/cli)에서 다룬다.

## The two things being measured

MCP Lens는 모든 툴에 대해 서로 독립적인 두 측정치를 대조한다. 정의가 매 프롬프트마다 소모하는
토큰 수와, 실제로 몇 번 호출되었는가다. 두 측정치는 서로에게 의존하지 않으며, 아래에서 설명하는
서로 다른 두 메커니즘으로 각각 수집된다.

## Definition scan: what a tool costs

`mcp-lens scan` (또는 확장의 온보딩 walkthrough)은 설정된 MCP 서버를 하나씩 짧게 띄워서 표준
`tools/list` 메서드를 호출하고, 돌아온 정의의 토큰 수를 센다. 하는 일은 이게 전부다.

```bash
mcp-lens scan
```

`scan`은 서버마다 한 줄을 출력한다. `<server>`는 서버 이름이고, 첫 번째 `<N>`은 그 서버가
노출하는 툴 개수, 두 번째 `<N>`은 그 툴들의 정의 토큰 총합이다.

```
- <server>: <N> tools, <N> tokens
```

이 스캔을 라이브 설정에 대고 돌려도 안전한 이유는 세 가지 성질 때문이다.

- LLM 토큰을 전혀 쓰지 않는다. 정의 토큰을 세는 것은 로컬 토크나이징이지 모델 호출이 아니다.
- 클라이언트 설정 파일을 절대 편집하지 않는다. 설정된 서버를 읽고 질의만 한다.
- stdio 서버는 프로세스를 띄워 툴 목록을 요청하고 종료시킨다. 서버를 계속 띄워 두거나 다른
  요청을 추가로 보내지 않는다.

결과, 즉 툴별 정의 토큰 수는 스캔 시점의 스냅샷으로 저장된다. 서버로 돌아가는 라이브 참조가
아니므로, 이후 서버의 툴이 바뀌어도 과거 스캔의 수치가 소급해서 바뀌지 않는다. `scan`을 다시
실행하면 새 스냅샷이 하나 더 찍힐 뿐이다.

## Usage collection: what a tool actually does

정의 비용만으로는 그 툴을 계속 켜 두었을 때 얼마가 드는지만 알 수 있다. 실제로 쓰이는지 알려면
클라이언트 내부에서 나온 호출 기록이 필요하고, 이를 위해 클라이언트별 훅과 플러그인이 존재한다
([Claude Code](/ko/guide/claude-code), [Codex](/ko/guide/codex),
[Gemini CLI](/ko/guide/gemini-cli) 참고).

각 훅은 툴 호출이 일어날 때마다 작은 메타데이터 레코드를 `~/.mcplens/inbox`에 원자적으로 쓴다.
그 큐를 데이터베이스로 비우는 것은 별개의 단계이며, 이를 수행하는 컴포넌트는 단 하나뿐이다.

::: warning inbox를 비우는 것은 VS Code 확장뿐이다
이것은 세부 사항이 아니라 현재의 한계다. `mcp-lens` CLI에는 큐를 비우는 경로가 아예 없다.
확장이 한 번도 실행되지 않으면 훅이 `~/.mcplens/inbox`에 쓴 레코드는 큐에 그대로 남고,
CLI 명령을 아무리 실행해도 `~/.mcplens/lens.db`에 도달하지 않는다. `mcp-lens hooks status`가
이를 드러낸다. `pending` 개수가 0으로 돌아가지 않고 계속 늘어나며, `mcp-lens hooks doctor`도
같은 상황에 대해 경고를 낸다.

그래서 훅만 설치한다고 CLI 전용 환경에서 `calls` 열이 채워지지는 않는다. `mcp-lens report`가
그래도 복구할 수 있는 값은 다른 경로에서 온다. 각 클라이언트 자신의 세션 로그를 파싱해서
사용량을 백필하는 것이다. 그 로그가 다루지 못하는 부분은 확장이 실행되어 큐를 비울 때까지
`calls`가 0으로 남는다. 그 사이 아무것도 유실되지는 않는다. 큐에 쌓인 레코드는 확장이 실행될
때마다 비워지기 때문이다.
:::

이 수집 경로가 실제 코딩 세션을 절대 방해하지 않는 것은 세 가지 성질 때문이다.

- 표준 출력은 항상 `{}`다. 훅은 클라이언트의 동작을 바꿀 수 있는 데이터를 절대 반환하지 않는다.
- 클라이언트를 절대 블록하지 않는다. 쓰기가 느리거나 실패해도 관찰 대상인 툴 호출을 지연시키지
  않는다.
- 네트워크 트래픽을 전혀 발생시키지 않고 런타임도 새로 띄우지 않는다. 로컬 파일시스템만
  건드린다.

레코드 자체는 의도적으로 얇다. 세션·턴·호출 ID, 클라이언트 이름, 서버와 툴 이름, 관찰 시각,
호출 소요 시간, 호출이 에러였는지 여부다. 호출의 실제 입력이나 출력은 포함하지 않는다.

## What is collected, and what never is

| Collected | Not collected |
|---|---|
| 세션·턴·호출 ID | 대화 본문과 프롬프트 |
| 클라이언트 이름, 서버와 툴 이름 | 툴 입력값 (`tool_input`) |
| 관찰 시각, 호출 소요 시간 | 툴 응답 (`tool_response`) |
| 호출이 에러였는지 여부 | 어시스턴트 응답 본문 |
| 스캔된 정의 토큰 수 | 소스 코드 |

모든 것은 로컬의 `~/.mcplens/lens.db` (SQLite)에 저장되며, `~/.mcplens/inbox`는 훅이 쓰는
중간 큐 역할을 한다. 일부 클라이언트가 별도로 남기는 원본 로그는 읽기 전용으로 취급한다.
MCP Lens는 그것을 절대 수정하거나 옮기지 않는다.

## The one exception: dependency analysis

위에서 설명한 측정은 전부 자기 기기 안에서만 실행된다. 툴을 꺼도 안전한지 판단하는 기능인
의존성 분석만 유일한 예외다. 자기 자신의 Claude 또는 Codex CLI 계정을 통해 외부 LLM을
호출하며, 그것도 무엇을 보내는지 검토하고 동의한 이후에만 실행된다.

전송되는 것:

- 서버와 툴 이름
- 툴 설명 텍스트
- 입력 스키마
- 툴 사이의 로컬 정적 참조 검사 결과
- 세션 내용은 뺀 호출 순서와 동시 발생 횟수
- 분석 대상 후보 목록과 판단 지침

전송되지 않는 것:

- 사용자 프롬프트와 대화 내용
- 소스 코드와 파일 경로
- 툴 입력값과 응답 본문
- 인증 토큰, 환경 변수, HTTP 헤더
- 원본 세션 로그와 원시 훅 레코드

설치 직후에는 아무것도 자동으로 실행되지 않는다. 설치 직후 확장은 스스로 스캔도 분석도 하지
않는다. 온보딩 walkthrough에서 LLM 제공자를 고르고, 예상 비용과 전송될 데이터를 확인하고,
동의한다. 그 시점부터 자동 스캔과 자동 분석은 옵트인이며 각각 독립적으로 제어되고, 동의를
철회하면 자동 분석은 즉시 멈춘다.

## Snapshots, not live references

모든 스캔과 모든 의존성 분석은 실행된 순간의 상태를 그대로 기록한다. 정의 토큰 수, 툴 본문,
분석 결과는 전부 타임스탬프와 정의 해시에 묶인 스냅샷으로 저장되며, 나중에 다시 해석되는
포인터가 아니다. 그래서 서버의 툴이 바뀐 뒤 `scan`을 다시 실행하면 과거 기록을 조용히 덮어쓰지
않고 새 행이 하나 생긴다. 지난주에 뽑은 리포트는 지난주에 사실이었던 내용을 그대로 반영한다.
