# 상태바 지표 재정의 — 보류 결정 기록

작성일: 2026-07-21
갱신: 2026-07-21 (선행 과제 완료로 상태 변경)
상태: **착수 가능** — 선행 과제였던 정의의 클라이언트 귀속이 main에 병합됨(`49fb46b`)

## 착수 전 요약 (새 세션용)

이 문서 하나로 작업을 시작할 수 있다. 필요한 배경은 아래에 다 있다.

- **할 일**: 상태바를 `Lens: 24 calls · 16.8k saved` → `Lens: 낭비 10툴 · 15.3k`로 바꾼다.
- **왜**: 현행 지표는 **인센티브가 역방향**이다 — 안 쓰는 MCP 서버를 추가하면 절약 수치가
  올라가고, 정리하면 내려간다 (아래 "결함 1" 참조).
- **선행 과제**: 완료됨. 정의가 클라이언트에 귀속되어 실체 없는 숫자가 사라졌다.
- **집계 대상**: `action`이 `remove` 또는 `filter-server`인 툴 (확신도 무관 — 아래 "②").
- **현재 실측** (2026-07-21, 귀속 적용 후):

| 클라이언트 | ② 낭비 판단 | ③ 확정만 |
|---|---|---|
| claude-code | **10툴 · 15,267tok** | 0툴 |
| codex | 0툴 | 0툴 |
| gemini-cli | **0툴** (귀속 전 92툴 34,753tok이었음) | 0툴 |
| 합계 | **10툴 · 15,267tok** | 0툴 |

- **바꿀 파일**: `packages/extension/src/statusBar.ts`(`formatStatus`),
  `packages/extension/src/extension.ts:112`·`:216`(`sessionSavings` 호출부).
- **남은 결정**: 아래 "착수 시 정할 것" 4가지.

## 왜 이 문서가 있나

상태바를 "지연 로딩으로 아낀 토큰"에서 "낭비로 판단한 툴의 수와 정의 비용 합"으로
바꾸기로 방향을 정했으나, 선행 과제가 끝나기 전에 구현하면 **지금보다 더 큰 오차**가
생기는 것이 실측으로 확인되어 보류한다.

## 현재 지표의 결함

`packages/extension/src/statusBar.ts` + `extension.ts:112`

```
Lens: 24 calls · 16.8k saved
saved = sessionSavings(input).savedTokens = potentialTokens − actualTokens
```

### 결함 1 — 인센티브가 역방향이다 (치명적)

`potentialTokens`는 스캔된 전 정의의 합, `actualTokens`는 로드된 것만의 합이다.
따라서 **쓸모없는 MCP 서버를 추가하면 절약 수치가 올라간다.**

| 행동 | potential | actual | saved |
|---|---|---|---|
| 안 쓰는 서버 추가 | +5,000 | +0 | **+5,000** |
| 안 쓰는 서버 정리 | −5,000 | −0 | **−5,000** |

낭비를 줄이라는 도구가 낭비를 추가하면 점수를 올려주고, 정리하면 깎는다.

### 결함 2 — 기준선이 존재한 적 없다

`potentialTokens`(34,753)는 "스캔된 92개 툴을 전부 업프론트로 깔았다면"의 값이다.
그러나 어느 클라이언트도 92개를 갖고 있지 않다 (Claude 5서버 / Codex 2서버 / Gemini 0서버).
세 클라이언트의 합집합인 가상의 존재가 기준선이다.

### 결함 3 — actualTokens는 세션 반복을 무시한다

`engine.ts`의 `sessionSavings`는 툴 키당 최댓값 하나만 남긴다.
`notion-search`는 실제로 4세션에서 로드됐지만 1회분만 계산된다.
매트릭스 트리는 누적(세션 수 곱)으로 바뀌었으나 상태바는 세션당 개념에 머물러 있어
두 표면의 축이 어긋나 있다.

### 결함 4 — 사용자의 성취가 아니고 행동을 유도하지 않는다

지연 로딩은 클라이언트의 내장 동작이다. 사용자가 한 일이 없고, 숫자를 봐도 할 일이 없다.

## 합의된 방향

상태바는 **"우리가 낭비로 판단한 툴의 개수 + 그 정의 비용의 합"**을 보여준다.

```
변경 전:  Lens: 24 calls · 16.8k saved
변경 후:  Lens: 낭비 10툴 · 15.3k
```

정리하면 숫자가 줄고, 쓸모없는 서버를 추가하면 늘어난다 — 인센티브가 바로 선다.

### 집계 대상은 "판단"이지 "확정"이 아니다

세 개념을 구분한다.

| | 정의 | 실측값(2026-07-21) |
|---|---|---|
| ① 호출 0회 | `callCount === 0` | 표시 대상 아님 |
| ② **낭비로 판단** | `action`이 `remove` \| `filter-server` | **claude-code 10툴 15,267tok** |
| ③ 낭비로 확정 | ② 중 `confidence !== 'low'` (리포트 `act` 버킷) | **전 클라이언트 0툴** |

③(`rollup.ts:137`의 `act`)은 현재 모든 클라이언트에서 0이라 상태바가 항상 `0`이 된다.
따라서 **②를 집계한다.** ①은 표시하지 않는다 — 어제 설치해 아직 안 써본 툴과
실제 낭비를 구분하지 못하기 때문이다.

## 왜 보류했었나 (해소됨)

②로 집계했을 때 귀속 적용 **전**의 실측값은 이랬다:

| 클라이언트 | ② 낭비 판단 (귀속 전) |
|---|---|
| claude-code | 10툴 · 15,267tok |
| codex | 0툴 |
| **gemini-cli** | **92툴 · 34,753tok** ⚠️ |
| 합계 | 102툴 · 50,020tok |

Gemini는 `~/.gemini/settings.json`에 MCP 서버가 **0개**인데 스캔된 전 정의가 붙어,
합계의 **69%가 실체 없는 숫자**였다. 그 상태로 상태바를 바꾸면 현행 지표(16.8k)보다
오차가 커지므로 보류했다.

원인은 두 겹이었다.

1. **정의가 클라이언트에 귀속되지 않았다.** 스캐너는 설정 출처를 알면서 저장 전에 버렸다.
2. **업프론트 모드에서 표시 필터가 꺼진다.** `visibleMatrixRows`(`engine.ts`)는 업프론트에서
   미사용 정의도 전부 표시한다. Gemini가 업프론트로 판정된 이유는 훅 도입 이전의 더미 MCP
   실험 세션 1건이 `dominantMode`를 단독 결정했기 때문이다 (`DEFERRED_OPAQUE`는 다수결에서
   제외되므로 증거 있는 세션 1건이 모드를 확정한다).

### 해소 (2026-07-21)

1번을 `client_servers` 매핑 테이블로 해결해 main에 병합했다(`49fb46b`).
설계: `docs/superpowers/specs/2026-07-21-정의-클라이언트-귀속-design.md`.

귀속 적용 후 재측정 결과 **gemini-cli의 92툴 34,753tok이 0으로 사라졌고**,
합계는 claude-code의 10툴 15,267tok만 남는다. 실기기 확인도 완료(gemini 하위에
실사용 이력이 있는 `lenstest` 1개만 잔존).

2번(단일 세션이 클라이언트 모드를 결정하는 취약점)은 **미해결**이나, 귀속 필터가
증상을 막으므로 이 작업의 차단 요인이 아니다.

## 착수 시 정할 것

- 문구 확정 (`Lens: 낭비 10툴 · 15.3k` 등)
- 클라이언트별 분리 여부 — 상태바는 한 줄이므로 합계인지, 최대 클라이언트인지, 전환식인지
- 축 — 세션당인지 누적인지 (조치 지표의 성격상 세션당이 자연스럽다)
- `②`가 0일 때의 표시
