# 문서 사이트 설계 (2026-08-09)

## 목적

MCP Lens의 공개 배포 문서 사이트를 만든다. 수준 기준은 AIMET 문서
(<https://qualcomm.github.io/aimet-pages/releases/latest/overview/install/quick-start.html>,
Sphinx + Furo)이다. 즉 진입용 Quick Start 한 장이 아니라 사이드바에 Quick Start·가이드·
개념·레퍼런스·FAQ가 모두 있는 풀 문서 사이트다.

## 확정된 결정

| 항목 | 결정 |
|---|---|
| 도구 | VitePress (기본 테마 + 소폭 커스텀) |
| 위치 | 루트 `website/` (npm workspaces에 포함하지 않음) |
| 배포 | GitHub Actions로 main 푸시 시 GitHub Pages, `base: /MCPLens-V2/` |
| 언어 | 영어 기본. `ko/` locale 골격만 준비하고 1차에는 영어 페이지만 작성 |
| 테마 모드 | 다크 기본(`appearance: 'dark'`), 헤더 토글로 라이트 전환 |
| README 중복 | README를 소개 + 지원 클라이언트 표 + 사이트 링크로 슬림화. 상세 설치·사용법은 사이트가 유일한 진실 |

## 사이트 구조

```
website/
  .vitepress/
    config.ts          # en 기본 + ko locale 골격, appearance: 'dark', base: /MCPLens-V2/
    theme/             # 최소 커스텀: 브랜드 색, 한글 대비 word-break: keep-all
  index.md             # 랜딩 (hero + feature 카드 3개)
  quick-start.md       # Requirements / Install(클라이언트별 code-group 탭) / Verify / First audit in 5 minutes
  guide/
    vscode-extension.md   # 주 배포 경로: .vsix 빌드·설치, 온보딩 워크스루
    claude-code.md        # 훅·플러그인 설치 상세
    codex.md
    gemini-cli.md
    reading-reports.md    # cost × usage 매트릭스 읽는 법, "무엇을 끄면 얼마 남는가" 결론까지
    dashboard.md
    global-actions.md     # 클라이언트 설정에서 툴 끄기 (Gemini CLI 미지원 명시)
  concepts/
    how-it-works.md       # 정의 스캔 + 사용 기록 대조, 스냅샷 수집 규약
  reference/
    cli.md                # 커맨드 레퍼런스
    configuration.md      # DB 경로(~/.mcplens/lens.db), 설정 파일
  faq.md                  # troubleshooting 포함
  ko/                     # 디렉토리와 locale 설정만, 페이지는 1차 범위 밖
```

- 클라이언트별 설치 분기는 VitePress `::: code-group` 탭으로 만든다. AIMET의
  ONNX/PyTorch 탭과 같은 UX다.
- 사이드바 좌측 전체 목차, 우측 페이지 내 목차(outline), 이전/다음 링크는
  기본 테마 기능을 그대로 쓴다.

## 내용 소스와 정확성

- 현재 루트 `README.md`의 상세 내용(설치 절차, 훅 설치, 사용법)을 사이트로 이관한다.
- 명령어·경로·수치는 실제 코드(`packages/cli`, `packages/extension`, `packages/*/package.json`)에서
  확인해 적는다. 추측으로 적지 않는다. 확인 불가 항목은 페이지에 넣지 않는다.
- 배포 문서이므로 본문은 전부 영어다 (CLAUDE.md 언어 규칙).

## 작성 원칙 (읽히는 문서의 기준, 모든 페이지 공통)

AIMET Quick Start가 잘 읽히는 이유를 규칙으로 옮긴 것이다. 페이지를 쓰는 서브에이전트와
리뷰어는 아래를 통과 기준으로 삼는다.

1. **과업 순서로 쓴다.** 개념 설명이 설치·실행 절차를 막아서지 않는다. 개념이 필요하면
   `concepts/`로 링크하고 본문은 다음 행동으로 직행한다.
2. **모든 코드 블록은 복붙 즉시 실행 가능해야 한다.** 플레이스홀더(`<version>` 등)는 꼭 필요한
   곳에만 쓰고, 쓰면 바로 위 문장에서 무엇으로 바꾸는지 말한다.
3. **실행형 명령 뒤에는 기대 출력을 보여준다.** 사용자가 "제대로 됐는지"를 출력 비교로 판단할 수
   있어야 한다. 출력이 길면 결정적인 줄만 발췌한다.
4. **분기는 탭으로 숨긴다.** 클라이언트별(Claude Code/Codex/Gemini CLI) 절차는 `::: code-group`
   탭으로 나눠, 독자가 자기 경로만 보게 한다. 본문에 "Codex의 경우에는…" 식 분기 문단을 늘어놓지
   않는다.
5. **절 하나는 스크롤 한 화면 안에 끝낸다.** 제목, 설명 두어 문장, 코드 블록. 그보다 길어지면
   절을 쪼갠다.
6. **Quick Start는 5분 안에 첫 성공까지 데려간다.** "설치 완료"가 아니라 "첫 스캔을 돌려
   cost × usage 매트릭스를 봤다"가 도착점이다.
7. **각 가이드 페이지 첫 문단은 "이 페이지를 끝내면 무엇이 되는가"를 말한다.** 목차 나열로
   시작하지 않는다.

## 빌드 격리

- `website/`는 루트 `package.json`의 workspaces에 넣지 않는다. 자체 `package.json`으로
  vitepress만 의존한다. 루트 `npm test`·`npm run build`·타입체크 체인에 영향이 없어야 한다.
- 문서 빌드 명령은 `website/` 안에서 `npm run docs:build` (vitepress build).

## 배포 파이프라인

- `.github/workflows/docs.yml`: main 푸시 중 `website/**` 변경 시 빌드 후 GitHub Pages 배포.
- `config.ts`의 `base`는 `/MCPLens-V2/`. 저장소 이름이 바뀌면 여기만 고친다.

## 완료 기준 (DoD)

- `vitepress build` 로컬 성공.
- dev 서버를 띄워 다크/라이트 모드 각각 스크린샷을 찍어 직접 확인하고 경로를 보고서에 남긴다
  (CLAUDE.md 화면 태스크 규칙). curl·빌드 성공은 이 요구를 대체하지 못한다.
- 모든 사이드바 링크가 404 없이 열린다 (`vitepress build`는 dead link에서 실패하므로
  빌드 성공이 곧 검증이다).
- README 슬림화가 같은 브랜치에 포함된다 (사본 이중화 금지 규칙).

## 1차 범위 밖 (명시적 제외)

- 한국어 페이지 본문 (구조만 준비)
- 커스텀 랜딩 디자인 (기본 hero 레이아웃 사용)
- 버전별 문서 분기 (릴리스가 생기면 그때 설계)
- 검색 서버 (기본 local search provider만 켠다)
