# 매트릭스 트리 누적 비용 표시 — 설계

작성일: 2026-07-21

## 문제

VS Code 확장의 매트릭스 트리가 **로드된 툴의 정의 비용을 표시하지 않는다.**
`matrixTree.ts:73`이 행 설명에 `responseTokens`(호출 응답 토큰)만 찍기 때문에,
컨텍스트에 로드됐지만 호출되지 않은 툴은 `0tok`으로 표시된다.

`0tok`은 "비용이 없다"는 **거짓 신호**다. 실제로는 정의가 컨텍스트에 올라간 만큼
토큰을 지불했다.

### 증거 (실측 DB, `~/.mcplens/lens.db`)

| 툴 | 정의 토큰 | 로드 세션 | 호출 | 화면 표시 |
|---|---|---|---|---|
| notion-query-meeting-notes | 3,374 | 1 | 0 | `0tok` |
| notion-update-page | 3,287 | 1 | 0 | `0tok` |
| notion-create-pages | 2,526 | 1 | 0 | `0tok` |
| notion-create-comment | 2,323 | 1 | 0 | `0tok` |

네 툴 합계 **11,510토큰**이 `0tok`으로 표시되고 있다.

### 수집 계층은 정상이다

조사 결과 이것은 **표시 계층만의 문제**다.

- 로그 어댑터는 로드 이벤트를 정상 수집한다
  (`adapters/claude/adapter.ts:82-95`의 `tool_reference` 파싱)
- 스캐너는 정의 토큰을 정상 산출한다 (`scanner.ts:63`, 정의 92건 적재됨)
- 엔진은 이 행들을 `loadPattern: 'search-pollution'`으로 정확히 판정한다
  (`engine.ts:120`)

엔진이 계산해 둔 `definitionTokens`·`loadedSessionCount`·`loadPattern`을
트리뷰가 **사용하지 않을 뿐**이다. 수집·엔진 계층은 수정하지 않는다.

## 설계

### 1. 누적 비용 공식

`packages/core`에 순수 함수로 추가한다. 확장과 리포트가 공유할 수 있는 위치에 둔다.

```
누적 비용 = (definitionTokens × loadedSessionCount) + responseTokens
```

- 앞항: 정의를 컨텍스트에 올린 비용. 로드된 세션마다 지불하므로 세션 수를 곱한다.
- 뒷항: 호출 응답 비용. 기존 집계 그대로.

`definitionTokens`가 `null`(스캐너 미커버)이면 앞항은 계산하지 않고 **미측정**으로 다룬다.
`0`으로 뭉개면 미측정과 실제 0을 구분할 수 없다.

**세션 수를 곱하는 근거**: 지연 로딩에서 정의 비용은 로드된 세션에서만 발생한다.
3세션에서 로드됐으면 3번 지불한 것이다. 로드되지 않은 세션은 0이므로,
세션을 많이 돌린 클라이언트가 부당하게 커 보이는 왜곡은 생기지 않는다.

### 2. 툴 노드 표시

```
현재:  notion-update-page  0회 · 0tok · filter-server?(후보)
변경:  notion-update-page  0회 · 3,287tok · filter-server (후보)
```

- 숫자는 천단위 구분자를 적용한다 (`markdown.ts:18`의 `fmt`와 동일 규칙)
- `definitionTokens`가 `null`이면 `미측정`으로 표시한다
  (`markdown.ts:98`의 기존 원칙 계승)

### 3. 추천 라벨에서 `?` 제거

`matrixTree.ts:70-72`의 `${action}?(후보)`를 `${action} (후보)`로 바꾼다.

`?`와 `(후보)`가 같은 불확실성을 두 번 표현해 중복이다.
판정 강등이 아니라 표시 강등이라는 기존 의미(스펙 결정사항 2)는 그대로 유지한다.

### 4. 서버 노드 집계

`matrixTree.ts:57`의 서버 노드 설명도 같은 누적 공식의 합으로 바꾼다.
그대로 두면 부모(`0tok`)와 자식(`3,287tok`)이 모순된다.

`zeroUsageServerNodes`(`matrixTree.ts:35`)의 `0회 · 0tok`은 유지한다.
로드도 호출도 없는 서버는 실제로 0이 맞다.

## 범위 밖

### 마크다운 리포트는 수정하지 않는다

`report/markdown.ts`는 **세션당(per-session)** 축을 유지한다.
리포트의 목적은 "제거하면 세션당 얼마 절약"이라는 **행동 권고**이고,
절약은 본질적으로 앞으로·세션당 개념이다.
트리뷰의 목적은 "지금까지 실제로 얼마 먹었나"라는 **소모 체감**이다.

두 축이 다른 것은 의도된 분리다. 한 화면에서 섞지 않는다.

### 엔진 판정 로직은 수정하지 않는다

임계값·추천 액션·확신도 산출은 그대로 둔다. 표시 계층만 바꾼다.

### 업프론트 클라이언트 누적은 이번에 다루지 않는다

업프론트 세션은 매 세션 전체 정의가 로드되지만 로드 이벤트가 남지 않아
`loadedSessionCount = 0` → 누적이 0으로 나온다.

이번 범위에서 제외하는 근거:

1. **영향 범위가 작다.** 실측 382세션 중 `UPFRONT` 판정은 2세션뿐이다
   (claude-code 1, gemini-cli 1).
2. **검증 불가능한 가정이 필요하다.** 세션별 연결 서버 목록이 DB에 없으므로
   "스캔된 전체 정의가 그 세션에 로드됐다"고 가정해야 한다.
   세션 이후 추가된 서버까지 소급 계산되어 **과대계상** 위험이 있다.
3. **더 큰 문제가 앞에 있다.** 전체의 83%(316세션)가 `DEFERRED_OPAQUE`로,
   훅 수집 경로가 모드를 하드코딩하기 때문이다 (`ingest/observations.ts:50`).
   업프론트 2세션보다 이 316세션의 모드 판별이 훨씬 큰 개선이다.

### 훅 수집 세션의 정의 비용은 과소계상된다

훅은 호출 시점에만 발생하므로 로드 이벤트를 남기지 않는다
(`ingest/observations.ts:37`이 `source === 'log'`인 관찰만 로드로 취급한다).
따라서 훅으로만 수집된 세션에서 호출된 툴은 `loadedSessionCount = 0`이 되어
**정의 비용이 빠진 채 응답 토큰만 집계된다.**

이는 과대계상이 아니라 **과소계상**이므로, `0tok` 거짓 신호를 없앤다는
이번 목표에 어긋나지 않는다. 표시되는 값은 언제나 실제 비용의 하한이다.

정확도가 필요해지면 "호출됨 = 로드됨" 역산으로 하한을 올릴 수 있으나,
이는 엔진의 증거 계층(`engine/evidence.ts`) 변경을 수반하므로 이번 범위에서 제외한다.

**후속 과제**: "훅 세션 모드 판별"을 별도 작업으로 분리한다.
그 작업이 끝난 뒤 업프론트 누적과 호출 기반 로드 역산을 함께 재검토한다.

## 테스트

### core — 누적 공식

- 로드 1세션·호출 0 → 정의 토큰 그대로
- 로드 3세션 → 정의 토큰의 3배
- 로드 0·호출 0 → 0
- `definitionTokens: null` → 미측정 (0이 아님)
- 정의 로드분과 호출 응답분이 합산되는가

### extension — `matrixTree.test.ts`

- 로드된 미호출 툴의 행에 정의 토큰이 표시되는가 (`0tok`이 아님)
- `definitionTokens: null` → `미측정` 표시
- 서버 노드 합계 = 자식 노드 합계
- `low` 확신 → `filter-server (후보)`, `?` 없음
- `zeroUsageServerNodes`는 `0회 · 0tok` 유지

유닛테스트는 픽스처 + `:memory:` DB만 사용한다 (터미널 병렬 안전).
