# 정의의 클라이언트 귀속 — 설계

작성일: 2026-07-21

## 문제

툴 정의가 어느 클라이언트 설정에서 왔는지 저장되지 않아,
**스캔된 전 정의가 모든 클라이언트에 조인된다.**

### 증거 (실측, 2026-07-21)

각 클라이언트의 실제 설정:

| 클라이언트 | 설정 파일 | MCP 서버 |
|---|---|---|
| claude-code | `~/.claude.json` | lenstest, lenstest2, deepwiki, notion, github |
| codex | `~/.codex/config.toml` | node_repl, computer-use |
| gemini-cli | `~/.gemini/settings.json` | **없음** |

그런데 매트릭스는 gemini-cli에 **93행**을 붙인다 — notion(Claude), vercel,
node_repl(Codex)까지 전부. 서버가 0개인 클라이언트에 34,753토큰이 귀속된다.

### 왜 gemini에서만 드러나나

지연 로딩 클라이언트에서는 두 겹의 보호가 우연히 작동한다.

1. 호출·로드는 세션 단위로 잘리므로(`splitByClient`), 남의 서버 행은 호출 0·로드 0이 된다.
2. `visibleMatrixRows`(`engine.ts:147-150`)가 지연 모드에서 그런 행을 숨긴다.

업프론트 모드는 "미사용 정의도 매 세션 실비용"이라는 전제이므로 **필터가 꺼진다.**
gemini-cli가 업프론트로 판정되는 이유는 훅 도입 이전의 더미 MCP 실험 세션 1건이
`dominantMode`를 단독 결정하기 때문이다 — `DEFERRED_OPAQUE`는 다수결에서 제외되므로
증거 있는 세션 1건이 모드를 확정한다.

즉 **현재 Claude·Codex 화면은 정상이지만, 업프론트 클라이언트를 제대로 다루려면
클라이언트 귀속이 선행되어야 한다.**

### 정보가 버려지는 위치

`packages/core/src/scanner/sources.ts:120-133`의 `collectAllSpecs`:

```ts
const byName = new Map<string, McpServerSpec>();
for (const source of ordered) {
  const { specs } = collectFromSource(source.kind, text);
  for (const spec of specs) {
    if (!byName.has(spec.name)) byName.set(spec.name, spec);   // source.kind 소실
  }
}
```

`source.kind`(`'claude-user' | 'claude-project' | 'codex' | 'gemini'`)를 루프 안에서
알고 있으나 맵에 담지 않는다. 이름 충돌 시 먼저 온 것만 남기므로,
같은 이름 서버가 두 클라이언트에 있으면 하나로 뭉개진다.

## 설계

### 1. 매핑 테이블 분리

정의 토큰은 **서버의 속성**이지 클라이언트의 속성이 아니다 — notion 서버는 누가 붙든
같은 20개 툴을 갖는다. 다른 것은 "누가 그 서버를 설정했나"뿐이다.

따라서 `tool_definitions`는 손대지 않고 매핑 테이블을 새로 만든다.

```sql
CREATE TABLE IF NOT EXISTS client_servers (
  client      TEXT NOT NULL,   -- 'claude-code' | 'codex' | 'gemini-cli'
  server_name TEXT NOT NULL,
  PRIMARY KEY (client, server_name)
);
```

PK가 `(client, server_name)`이므로 **한 서버가 여러 클라이언트에 매핑되는 것을 지원한다.**
`deepwiki`를 Claude와 Codex 양쪽에 설정하면 두 행이 생기고, 트리에서 각 클라이언트에
자기 세션 기준의 비용으로 나타난다.

정의 중복 저장도, 재토크나이즈도 없다.

**공유 계약 영향**: `schema.sql`은 CLAUDE.md가 지정한 공유 계약이나, 기존 테이블 변경 없이
추가만 하므로 `CREATE TABLE IF NOT EXISTS`로 마이그레이션이 자동이다.
`packages/core/src/types.ts`는 **변경하지 않는다** — `ClientId`가 이미 존재하므로
새 타입이 필요 없다.

### 2. 스캔 시 출처를 살린다

`collectAllSpecs`의 **스캔 대상 dedupe는 유지한다** — 서버당 한 번만 스캔하면 되고,
정의는 클라이언트와 무관하기 때문이다. 귀속은 별도 맵으로 반환한다.

```ts
attribution: Map<string, Set<ClientId>>   // serverName → 그 서버를 설정한 클라이언트들
```

소스 종류 → 클라이언트 매핑:

| `source.kind` | `ClientId` |
|---|---|
| `claude-user` | `claude-code` |
| `claude-project` | `claude-code` |
| `codex` | `codex` |
| `gemini` | `gemini-cli` |

`claude-user`와 `claude-project`는 모두 `claude-code`로 접힌다 — 프로젝트 스코프 서버도
클라이언트 수준에서는 Claude의 것이다.

### 3. 저장은 클라이언트 단위 전체 교체

설정에서 서버를 지우면 매핑도 사라져야 하므로, 해당 클라이언트의 행을 지우고 새로 쓴다.

**단, 설정을 온전히 관찰한 클라이언트에 한한다.** 권한 오류 등으로 읽지 못한
클라이언트는 기존 매핑을 보존한다. 읽기 실패를 "서버 없음"으로 해석하면
매핑이 통째로 날아가고, 그 클라이언트의 모든 정의가 화면에서 사라진다.

`collectAllSpecs`는 읽기 실패 시 `continue`하므로(`sources.ts:126-130`), 어느 소스를
실제로 읽었는지 함께 반환해야 이 구분이 가능하다.

**"온전히 관찰"의 정의 — 파일 부재와 읽기 실패를 구분한다.**

한 클라이언트가 여러 소스를 가질 수 있다 (claude-code는 `claude-user` 1개 +
`claude-project` N개). 또한 설정 파일이 **없는 것은 정상**이다 — 프로젝트별 `.mcp.json`은
대부분 존재하지 않고, Gemini를 안 쓰면 `~/.gemini/settings.json`도 없다.

따라서 두 실패를 구분한다.

| 상황 | 해석 | 매핑 |
|---|---|---|
| 파일 없음 (`ENOENT`) | 정상 — 그 소스에 서버가 없다 | 교체 대상에 포함 |
| 그 외 읽기 오류 (권한 등) | 관찰 실패 | 그 클라이언트는 **보존** |

한 클라이언트의 소스 중 **`ENOENT`가 아닌 오류가 하나라도 있으면** 그 클라이언트는
교체하지 않는다. 그래야 Gemini처럼 설정 파일이 아예 없는 정상 케이스에서
"서버 0개"가 올바르게 반영되고, 권한 오류로 못 읽은 경우에만 기존 값이 유지된다.

### 4. 엔진 필터링

`EngineInput`(`engine.ts` — `types.ts` 아님)에 **선택 필드**를 추가한다.

```ts
serversByClient?: Map<ClientId, Set<string>>;
```

`splitByClient`가 각 클라이언트 분할을 만들 때, 그 클라이언트에 매핑된 서버의 정의만
통과시킨다.

두 가지 안전장치를 둔다.

**(a) 필드가 없으면 필터링하지 않는다.**
기존 호출부와 테스트가 그대로 동작하고, 스캔 전 DB(매핑 테이블이 빈 상태)에서도
현재와 동일하게 작동한다. 마이그레이션 중 화면이 비는 사고를 막는다.

**(b) 실사용 이력이 있는 행은 걸러지지 않는다.**
매트릭스 행은 `정의 ∪ 호출 ∪ 로드`의 합집합이므로(`engine.ts:57-67`),
설정에서 지운 서버라도 그 클라이언트 세션에서 실제 호출·로드가 있었으면 계속 보인다.
필터는 **정의만 있는 행**에만 걸린다. 과거 사용 이력을 지우지 않는다.

### 5. 기대 결과

```
전:  gemini-cli  세션 3개 · 0tok
       notion 20툴 / vercel 30툴 / node_repl 3툴 / deepwiki 3툴 ... 93행

후:  gemini-cli  세션 3개 · 0tok
       (설정된 서버 없음 — 실사용 이력이 있는 행만 표시)
```

claude-code에는 Claude 서버만, codex에는 Codex 서버만 귀속된다.

## 범위 밖

### 업프론트 누적 계산

이 설계는 클라이언트 귀속까지만 다룬다. 업프론트 클라이언트의
`정의 × 세션 수` 누적 계산은 별도 과제다 — 귀속이 선행되어야 계산이 성립하지만,
현재 업프론트 판정 세션은 실사용이 아닌 더미 실험 2건뿐이라 지금 만들 근거가 없다.

### Gemini 모드 판정 논리

Gemini는 지연 로딩 기능이 없으므로 모드는 세션 속성이 아니라 클라이언트 속성이다.
그러나 현재 어댑터는 `toolCalls.length > 0 ? 'UPFRONT' : 'DEFERRED_OPAQUE'`
(`adapters/gemini/adapter.ts:179`)로 세션마다 판정한다. 논리적으로 틀렸으나,
이 설계의 귀속 필터가 적용되면 증상(93행 노출)이 사라지므로 별도로 다룬다.

### 단일 세션이 클라이언트 모드를 결정하는 취약점

`dominantMode`는 증거 있는 세션 1건으로 모드를 확정한다. 새 클라이언트를 처음 붙일 때마다
같은 일이 반복될 수 있으나, 이 설계의 범위가 아니다.

### 상태바 지표 재정의

`docs/decisions/2026-07-21-상태바-지표-재정의.md`에 기록된 보류 과제.
이 설계가 그 선행 조건이다.

## 테스트

### sources — 귀속 맵

- 각 소스 종류가 올바른 `ClientId`로 접히는가 (`claude-user`·`claude-project` → `claude-code`)
- 같은 이름 서버가 두 소스에 있으면 **두 클라이언트 모두**에 귀속되는가
- 스캔 대상 specs는 여전히 이름 기준 dedupe되는가 (서버당 1회 스캔)
- 읽지 못한 소스가 반환값에서 구분되는가

### store — 매핑 저장

- 클라이언트 단위 전체 교체가 동작하는가 (설정에서 지운 서버가 매핑에서 사라짐)
- 읽기 실패한 클라이언트의 기존 매핑이 보존되는가
- 한 서버가 여러 클라이언트에 매핑될 수 있는가
- 빈 DB에서 `serversByClient`가 빈 맵을 돌려주는가

### engine — 필터링

- `serversByClient`가 없으면 필터링하지 않는가 (기존 동작 보존)
- 매핑된 서버의 정의만 그 클라이언트에 통과하는가
- 매핑에 없어도 **호출 이력이 있는** 행은 남는가
- 매핑에 없어도 **로드 이력이 있는** 행은 남는가
- 서버가 0개인 클라이언트는 정의 기반 행이 0인가

유닛테스트는 픽스처 + `:memory:` DB만 사용한다 (터미널 병렬 안전).
