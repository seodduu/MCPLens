## 3. T1 사양: 공유 계약

설계 3.1·3.2절의 인터페이스를 그대로 옮긴다. 아래는 그 외에 T1이 결정해야 하는 것이다.

### 3.1 개명 대응표

| 지금 | 바뀌는 이름 | 필드 변화 |
|---|---|---|
| `RecommendationEvidence` | `ObservationFacts` | 없음. 필드 전부 유지 |
| `ServerEvidence` | `ServerObservationFacts` | 없음. 필드 전부 유지 |
| `Recommendation` | `ToolFacts` | `action`·`confidence`·`reason`·`reasonParts`·`evidenceLabel` 제거. `basis`·`loadedNotCalledSessions`·`dependents` 추가. `evidence` → `observation` |
| `ServerVerdict` | `ServerFacts` | `action`·`confidence`·`reason` 제거. `measuredPerSessionTokens` → `perSessionTokens`. `toolCount`·`calledToolCount` 추가. `evidence` → `observation` |

`evidenceLabel`의 네 값(`measured`/`lower-bound estimate`/`assumed full load`/`not measurable`)은
`ToolFacts.basis`의 세 값으로 접힌다.

| 옛 `evidenceLabel` | 새 `basis` |
|---|---|
| `measured` | `measured` |
| `lower-bound estimate` | `estimated` |
| `assumed full load` | `estimated` |
| `not measurable` | `unknown` |

`assumed full load`가 `estimated`로 가는 이유는 그것이 가정에 근거한 수치이고, 설계 3.4절이
가정에 근거한 수치를 단독 숫자로 못 쓰게 하기 때문이다.

### 3.2 `ToolRow`의 필드 교체

`types.ts` 261행의 `recommendation: Recommendation` 은 `facts: ToolFacts` 가 된다. 같은 인터페이스의
`callCount`·`responseTokens`·`loadedSessionCount`·`sessionCount`·`reliability`·`loadPattern` 은
그대로 둔다. 전부 사실이다.

### 3.3 T1 테스트

T1은 타입만 바꾸므로 런타임 테스트가 없다. 판정 기준은 타입체크다.

```
npx tsc --noEmit -p packages/core/tsconfig.json
```

이 명령이 **`engine`·`report` 의 오류만** 남기고 `types.ts` 자체에는 오류가 없어야 한다. 남은
오류 목록을 보고서에 그대로 붙인다. 그것이 T2·T3의 작업 목록이다.

## 4. T2 사양: 엔진에서 판정 제거

### 4.1 지우는 상수

`serverVerdict.ts` 의 `LOW_SESSIONS = 5`, `LOW_DAYS = 3`, `HIGH_SESSIONS = 10`, `HIGH_DAYS = 7`
을 지운다. 이 넷이 판정의 전부였고, 결정 문서가 근거를 부정했다.

**관측 창 계산에 쓰이는 상수는 지우지 않는다.** `MS_PER_DAY` 같은 것은 사실 산출에 쓰인다.
지우기 전에 그 상수가 등급 산출에만 쓰이는지 호출처로 확인한다.

### 4.2 `serverFacts.ts`가 하는 일

서버 하나에 대해 설계 3.2절의 `ServerFacts`를 만든다. 분기가 없다. 세고 더할 뿐이다.

```ts
export function serverFacts(server: string, ctx: FactsContext): ServerFacts
```

지금 `serverVerdict.ts` 151행과 238행의 `return { action: 'keep', confidence: 'high', ... }`
같은 이른 반환이 전부 사라진다. 모든 서버가 같은 경로로 사실을 만든다.

### 4.3 `healthGate.ts`

수집 건강도 게이트는 남긴다. **그것은 "이 데이터를 믿어도 되는가"이지 "이 툴을 꺼라"가 아니다.**
다만 게이트 통과 여부를 확신도 등급으로 표현하던 부분은 사실로 바꾼다. 훅 커버리지가 부족하면
등급을 낮추는 대신 **수치를 표시하지 않는다**(`basis: 'unknown'`). 근거가 모자란 값을 등급으로
할인해서 보여주느니 안 보여주는 쪽이 설계 2절 원칙에 맞다.

### 4.4 T2 테스트 케이스와 단언 (전량)

`packages/core/test/engine/serverVerdict.test.ts` 를 `serverFacts.test.ts` 로 옮기고 아래로
바꾼다. 기존 케이스 중 등급을 단언하던 것은 전부 지운다.

- `counts tools and called tools for a server`: 툴 10개 중 3개가 관측 창에서 호출된 픽스처에서
  `toolCount`가 10, `calledToolCount`가 3이다.
- `per-session tokens include instructions`: 정의 합 2,900, instructions 340인 픽스처에서
  `perSessionTokens`가 3,240이고 `instructionsTokens`가 340이다.
- `unmeasured name-list entries are counted, not filled`: 툴 10개 중 4개의 `nameListTokens`가
  null인 deferred 픽스처에서 `unmeasuredNameListEntries`가 4이고, `perSessionTokens`가 나머지
  6개의 합이다. 0으로 채우거나 평균으로 메우지 않는다.
- `observation facts carry the window as measured`: 관측 창이 세션 12개·9일인 픽스처에서
  `observation.configuredSessions`가 12, `observation.observedDays`가 9다.
- `no action or confidence field exists on the result`: 반환 객체에 `action`·`confidence` 키가
  없다(`Object.keys`로 단언).

`engine.test.ts` 에는 아래를 더한다.

- `tool facts carry basis measured under upfront`: eager 픽스처에서 `facts.basis`가 `measured`다.
- `tool facts carry basis estimated under deferred`: deferred 픽스처에서 `estimated`다.
- `tool facts carry basis unknown when the scanner did not cover the tool`: 스캐너가 못 덮은
  픽스처에서 `unknown`이고 `perSessionTokens`가 null이다.
- `loaded-not-called sessions are counted from load and call records`: 로드 3세션, 호출 1세션인
  deferred 픽스처에서 `loadedNotCalledSessions`가 2다.
- `dependents list the tools that break when this tool is off`: 의존 픽스처에서 그 목록이
  정적 분석 결과와 같다.

## 5. T3 사양: 리포트 모델과 렌더러

### 5.1 버킷 제거

`ReportBucket` 타입과 `rollup.ts` 의 버킷 분류, `markdown.ts` 의 `bucketTitle`·`renderActGroup`·
`renderCandidateGroup`·`renderInspectBucket`·`renderHealthyBucket` 을 전부 지운다.

대신 설계 3.3절의 `ReportServerSection` 하나를 서버마다 만든다.

### 5.2 정렬

`ReportOptions` 에 `sort: 'savings' | 'idle' | 'calls'` 를 더한다. 기본값 `'savings'`.

설계 4.1절대로 **단일 측정값 비교만** 쓴다. 비교 함수에 곱셈이나 덧셈이 들어가면 위반이다.
동률이면 툴 이름 사전순으로 끊어 출력이 결정적이 되게 한다.

### 5.3 추정값 표기

설계 3.4절을 렌더러가 강제한다.

```ts
// basis 별 렌더링. estimated 는 오차 없이 출력할 수 없다.
function tokenCell(facts: ToolFacts, errorRate: number | null): string
```

- `measured`: `410`
- `estimated`: `~410 (estimated, +-285% error)`. `errorRate`가 null이면 `~410 (estimated)`
- `unknown`: `unmeasured`

합계는 `measured`와 `estimated`만 더하고, `unknown`인 툴 수를 각주로 적는다.

### 5.4 T3 테스트 케이스와 단언 (전량)

`packages/core/test/report/rollup.test.ts` 와 `markdown.test.ts` 를 고친다.

- `groups tools by server with no buckets`: 결과에 `bucket` 키가 없고 서버 수만큼 섹션이 있다.
- `sorts by savings descending by default`: `perSessionTokens` 410/380/350인 픽스처에서 그 순서다.
- `sorts by idle when asked`: `lastCalledAt`이 없는 툴이 맨 위이고 그다음이 가장 오래된 순이다.
- `sorts by calls ascending when asked`: 호출 0회가 맨 위다.
- `ties break by tool name`: 같은 `perSessionTokens` 두 툴이 이름 사전순으로 나온다.
- `renders an estimated value with its error rate`: `basis: 'estimated'`, 오차 285인 툴 행에
  `~410 (estimated, +-285% error)` 가 있다.
- `renders an unmeasured value as text, not zero`: `basis: 'unknown'` 인 툴 행에 `unmeasured`가
  있고 `0`이 없다.
- `excludes unmeasured tools from the total and footnotes the count`: 툴 3개 중 1개가 `unknown`인
  픽스처에서 합계가 나머지 2개의 합이고 각주에 `1`이 있다.
- `states the sort key in the header`: 출력에 `sorted by savings` 가 있다.
- `counts never-called tools as a fact line`: 20개 중 18개가 호출 0회인 픽스처에서
  `18 of 20 tools were never called in this window.` 가 있다.
- `no output line tells the user what to do`: 출력 전체에 `Act now`, `recommend`, `should`,
  `confidence` 문자열이 하나도 없다.

마지막 케이스가 이 태스크의 핵심 방어다. 문구가 슬그머니 권고로 돌아오는 것을 막는다.

## 6. T4·T5·T6 사양: 소비자 세 개

셋 다 core의 새 계약을 소비하기만 한다. 공통 규칙은 아래다.

- **core의 공개 API만 쓴다.** `packages/core/src/...` 내부 경로를 직접 import 하지 않는다.
- **수치를 다시 계산하지 않는다.** 합계·비율은 core가 준 값을 그대로 쓴다. 클라이언트는 포맷만
  맡는다.
- **정렬 컨트롤을 만든다.** 현재 기준을 화면에 표시하고 사용자가 바꿀 수 있어야 한다(완료 조건 4).
- **스크린샷을 찍어 직접 본 뒤** 그 경로를 보고서에 남긴다. 테스트 통과나 `curl` 확인은 이 요구를
  대체하지 못한다.
- 한글 본문이 있으면 `word-break: keep-all` 과 한글에 맞춘 자간·행간을 적용한다.

### 6.1 T4 CLI

지금 CLI 리포트가 판정에 의존하는 자리는 셋이다. 실제 코드를 확인한 결과 `--confidence-floor`
같은 인자는 없고, 전부 출력 내부에 있다.

| 자리 | 지금 | 바뀌는 것 |
|---|---|---|
| 표 컬럼 (`COLUMNS` 59행) | `action`, `confidence`, `reason` 세 컬럼 | 세 컬럼 제거. `lastCalled`, `observed` 추가 |
| 행 정렬 (231행) | 확신도 등급 순(`RANK`) | 설계 4.1절의 단일 측정값 정렬 |
| 확정/후보 분리 (235~236행) | `confidence !== 'low'` 로 갈라 출력 | 분리 없음. 한 목록 |
| 서버 경고 줄 (24행) | `! server X: <reason> (<confidence>)` | 서버별 사실 줄로 교체 |

`--sort savings|idle|calls` 를 더한다. 기본값 `savings`. 설계 5.1절의 출력 모양을 그대로 낸다.

## 8. 자체 검토

- 완료 조건의 모든 항목이 태스크 하나 또는 통합 게이트에 대응한다.
- 공유 계약(T1)이 선행 태스크로 분리됐고, 병렬 태스크(T4·T5·T6)의 쓰기 파일이 겹치지 않는다.
- 상위 모델은 공유 계약(T1)과 판정 분기 해석(T2)에만 배정했고 사유를 표에 적었다.
- 테스트는 픽스처와 인메모리 DB만 쓴다. 실 DB를 만지는 태스크가 없다.
- 스키마를 건드리지 않으므로 마이그레이션 번호 역전이 발생할 수 없다.
- 화면을 만드는 세 태스크에 스크린샷 요구를 명시했다.
- 판정이 문구나 정렬로 되돌아오는 경로를 두 단언이 막는다. T3 의
  `no output line tells the user what to do` 와 완료 조건 4번의 합성 점수 금지다.
- `pilot/**` 을 범위 밖으로 못 박았다. 파일럿이 옛 JSON 을 읽어야 과거 배치 재빌드가 유지된다.
