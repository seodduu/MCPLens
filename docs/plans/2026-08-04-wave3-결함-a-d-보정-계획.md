## 결함 A: 스캔 판정이 definition 존재를 스캔 완료로 오인한다

### 관측된 사실

`tool_definitions` 95행은 2026-07-19~21 스캔분이고 `tool_definition_bodies` 테이블은
그보다 뒤에 추가됐다. 실기기 DB는 definition 95행 / body 0행 상태였다.

`scanDecision.ts:20`이 재스캔 대상을 definition 존재로 거른다.

```ts
const targets = args.specs.filter(
  (s) => !args.knownServers.has(s.name) && !(args.unsupported?.has(s.name)));
```

`autoScan.ts:110`이 그 집합을 definition에서 만든다.

```ts
const knownServers = new Set(store.allDefinitions().map((d) => d.serverName));
```

definition이 있으니 전 서버가 걸러져 `kind: 'skip'`이 되고 body는 영원히 안 채워진다.

여파는 스캔에서 끝나지 않는다. `extension.ts:459`의 `disable`이 body를 못 찾으면 조용히
반환하고, `matrixTree.ts:179`의 `canDisableGlobally`도 성립하지 않는다. 3차 E2E에서
`mcp-lens scan` CLI로 body 86행을 수동 적재한 뒤에야 분석과 액션이 동작했다.

### 판정 기준을 body 존재로 바꾸는 것이 안전한 이유

`upsertScanResult`는 definition과 body를 한 트랜잭션에서 함께 쓴다(`store.ts:306`).
따라서 스캔이 성공했다면 둘 다 있고, 툴이 0개인 서버라면 둘 다 없다.

즉 "definition은 있는데 body가 없다"는 상태는 body 테이블 도입 이전에 스캔된
레거시 DB에서만 발생한다. 판정 기준을 body로 바꿔도 오늘 재스캔되지 않던 서버가
새로 무한 재스캔에 빠지는 경우는 생기지 않는다. 툴 0개 서버는 지금도 definition이
없어 이미 매번 대상이 된다.

인증이 필요해 스캔에 실패하는 서버(github, figma)도 definition이 없으므로 동작이 바뀌지 않는다.

### 변경 1: core 저장소에 body 보유 서버 조회를 추가한다

`packages/core/src/store/store.ts`의 `allDefinitions()` 바로 아래에 넣는다.

   * 정의 body가 실제로 적재된 서버명. 스캔 완료 판정의 기준이다.
   * definition만 있고 body가 없는 서버는 body 테이블 도입 이전에 스캔된
   * 레거시 상태이므로 재스캔 대상으로 남아야 한다.

## 결함 D: hook의 tool-before가 상관 후보에서 제외돼 건강도가 회복 불가다

### 관측된 사실

`eligibility.ts:32`가 건강도를 전역 액션 게이트로 둔다.

```ts
if (input.collectionHealth !== 'healthy' && input.collectionHealth !== 'log-only') {
  reasons.push('collection-health-unsafe');
}
```

실기기 Codex는 `degraded`였고 회복되지 않았다. 원인은 `collectionHealth.ts:39`다.

```ts
const COMPLETED_CALL_PHASES = new Set<HookPhase>(['tool-after', 'tool-failure']);
```

이 집합이 hook 후보 수집(`collectionHealth.ts:80`)과 log miss 계산(같은 파일 `:92`)에
동시에 쓰인다. 그런데 실기기 Codex는 lenstest2 MCP 호출에서 hook을 `tool-before`만 남겼다.
hook 후보 집합이 비어 log `tool-after`가 전부 miss가 됐다.

상관키는 완벽히 일치했다.

```
hook | tool-before | native:db3f1408… | high
log  | tool-after  | native:db3f1408… | high
```

같은 native 해시에 confidence high다. 짝지을 데이터는 다 있는데 phase 필터가 hook 쪽을 버렸다.

실측으로 확인했다. 회복을 노려 실제 MCP 호출을 2회 추가했더니 불일치 계수가 40에서 42로 늘었다.

### 코드모드 검색은 이 문제의 원인이 아니다

miss는 log 관측 중 phase가 `tool-after`/`tool-failure`인 것만 대상으로 센다.
코드모드 검색은 log `tool-before`로 들어오므로 애초에 miss 계산에 포함되지 않는다.
따라서 이번 보정은 hook 쪽 필터만 건드리면 된다.

### 설계 판단: hook의 tool-before를 커버리지 증거로 인정한다

건강도가 재는 것은 "hook 수집기가 살아서 이 호출을 보고 있는가"다. 특정 호출에 대해
hook이 `tool-before`를 남겼다면 그 호출을 hook이 관측한 것이다. Codex가 MCP 호출에
완료 단계 hook을 안 남기는 것은 클라이언트 특성이지 수집기 장애가 아니다.

대가는 명시해 둔다. hook이 시작만 보고 완료를 못 본 호출도 match로 세게 된다.
건강도는 수집기 생존을 재는 지표이지 duration 완전성을 재는 지표가 아니므로 감수한다.
duration이 필요한 계산은 이미 log 쪽 `tool-after`를 쓴다.

### 변경: 상관 후보 phase 집합을 log와 hook으로 분리한다

`packages/core/src/health/collectionHealth.ts:39`를 다음으로 대체한다.

```ts
/** log 쪽에서 상관 성사 여부를 따지는 대상. 완료된 호출만 센다. */
const COMPLETED_CALL_PHASES = new Set<HookPhase>(['tool-after', 'tool-failure']);

/**
 * hook 쪽에서 커버리지 증거로 인정하는 단계.
 * Codex는 MCP 호출에 완료 단계 hook을 남기지 않고 tool-before만 남긴다.
 * 완료 단계만 인정하면 상관키가 일치하는데도 전부 miss가 되어 건강도가
 * degraded로 굳고, 회복 조건인 2연속 match가 영원히 성립하지 않는다.
 * 건강도는 수집기 생존을 재는 지표이므로 시작 단계 관측도 커버리지로 인정한다.
 */
const HOOK_COVERAGE_PHASES = new Set<HookPhase>(['tool-before', 'tool-after', 'tool-failure']);
```

`collectionHealth.ts:81`의 hook 수집 조건을 바꾼다.

```ts

      || !HOOK_COVERAGE_PHASES.has(observation.phase)

```

`collectionHealth.ts:92`의 log 조건은 `COMPLETED_CALL_PHASES` 그대로 둔다.

`hookTimesByKey`의 splice 기반 1:1 소비(`:99`)는 그대로다. 한 호출에 hook
`tool-before`와 `tool-after`가 모두 있으면 후보가 2개가 되고 log `tool-after` 하나가
그중 하나만 소비한다. 기존 동작과 같다.

## 다음 회차 E2E 판정 기준

이 보정이 통합되면 4차 실환경 E2E에서 아래 두 가지가 새 합격 기준이 된다.

1. **레거시 DB 자동 치유.** definition만 있고 body가 없는 상태에서 확장을 띄우면
   재스캔이 일어나 body가 적재되고, 별도 CLI 개입 없이 분석과 액션이 동작해야 한다.
2. **Codex 액션 노출.** 실제 MCP 호출로 hook `tool-before`와 log `tool-after` 쌍이
   2연속 생기면 건강도가 `degraded`에서 벗어나고, zero-call 후보에
   `Disable Globally`가 노출돼야 한다. 그래야 3차에서 못 돈 indirect regret 2건 확인으로
   넘어갈 수 있다.

3차 E2E 절차서의 결함 두 가지도 함께 고친다. 새 worktree에서는 `npm run build`를 테스트보다
먼저 돌리고, 후보 툴은 로드나 호출 관측이 있는 것 중에서 고른다. 관측이 0건이면
`engine.ts:154`의 필터에 걸려 트리에 나타나지 않는다.
