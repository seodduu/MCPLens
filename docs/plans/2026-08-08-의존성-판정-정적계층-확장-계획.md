# 의존성 판정 정적 계층 확장 계획 (A·B·F·E·D)

작성일: 2026-08-08
기점 브랜치: `main`

---

## 1. 배경과 문제

현재 의존성 판정은 3계층이다. 1계층 정적 참조(`staticRefs.ts`), 2계층 호출 연쇄
(`callChains.ts`), 3계층 LLM 의미 판정(`inferenceCli.ts`).

문제는 **2계층이 가장 필요한 시점에 데이터가 없다**는 것이다.

1. 워크스루 2단계에서 훅을 설치한다. 새로 추가한 서버의 호출 기록은 0건이다.
2. 워크스루 3단계에서 곧바로 분석한다. `autoScan` 경로도 스캔 직후 `afterScan`으로 분석을 잇는다.
3. `findCallChainDependencies`의 조건(`before >= 3 && before / bSessions >= 0.8`)을 만족할 방법이 없다.
4. LLM에 전달되는 `callChainSummary`가 전부 빈 배열이다.
5. 즉 1계층과 3계층만으로 판정된다.

로그 워처의 `backfill()`이 확장 활성화 시 과거 세션 로그를 훑으므로, Lens 설치 이전부터
MCP를 쓰던 사용자에게는 기록이 있다. 그러나 **새로 추가한 서버는 정의상 항상 기록이 0건**이고,
그 시점이 바로 자동 분석이 걸리는 시점이다.

두 번째 문제는 캐시다. `analyzeUncachedServers`의 캐시 키가
`definition_set_hash + analysis_rules_version` 둘뿐이라, 나중에 호출 기록이 쌓여도
서버 정의가 그대로면 재분석이 일어나지 않는다. 첫날의 데이터 없는 판정이 영구히 남는다.

### 놓치고 있는 신호

1계층은 **툴 이름 문자열**만 찾는다.

```ts
const regex = exactToolRegex(candidate.toolName);
```

`book_reservation`의 설명이 `"Book a table."`이고 필수 입력이 `["restaurant_id"]`인 경우,
`search_restaurants`라는 문자열이 없으므로 1계층이 못 잡는다. 그러나 `restaurant_id`는
사람이 지어낼 수 없는 값이고, 그것을 만드는 툴이 서버에 하나뿐이라면 그 툴은 삭제 금지 대상이다.

이 계획은 **호출 기록 없이 정의만으로 판정 가능한 신호**를 세 종류 추가하고,
시간이 지나면 2계층이 스스로 재참여하게 만든다.

## 2. 확정된 결정

| 항목 | 결정 | 근거 |
|---|---|---|
| 새 계층의 판정 강도 | **`Review required`까지만** | `merge.ts`의 현행 관례 유지. 새 증거는 `blockers`에 합류만 하고 merge 분기를 안 건드린다. `Independent` 차단이라는 목적은 100% 달성되고, 기존 merge 테스트가 안 깨진다. |
| 탐색 범위 | **같은 서버 안** | 기존 1·2계층과 동일. 서버가 다르면 `id`·`name`·`url` 같은 흔한 필드명이 우연히 겹칠 확률이 높고, 오탐은 "못 끄는 도구"가 되어 절감 기회를 잃는다. |
| `outputSchema`의 `definitionTokens` 포함 | **포함 + 전체 재스캔** | 클라이언트가 실제로 컨텍스트에 넣는 것과 일치시킨다. 토큰 회계 정확도가 이 도구의 존재 이유다. |

### 판정 강도 결정의 전제 (코드 확인 결과)

설계 문서 7-3절은 "정적 참조가 확정되면 즉시 `Dependent`"라고 적었지만,
**실제 `merge.ts`는 그렇게 동작하지 않는다.**

```ts
if (llm?.status === 'Dependent') { ...Dependent... }
if (blocker !== undefined) {
  return scrubExplanations({ ...status: 'Review required'... });
}
```

`staticRefs`와 `callChains`의 증거는 `blockers`에 들어가 `Review required`로 내려갈 뿐이고,
`Dependent` 확정은 LLM 몫이다. 이 계획의 새 계층 셋도 같은 경로를 쓴다.
따라서 **`merge.ts`의 분기 로직은 변경하지 않는다.** 입력 필드만 추가한다.

## 3. 범위

### 범위 안

- **A**: 입력 스키마의 불투명 필드로 생산자·소비자 관계 탐지 (`schemaFlow.ts`)
- **B**: `outputSchema` 수집. A의 어간 추측을 필드명 대조로 승격
- **F**: 상태 소비자 탐지 (`stateConsumer.ts`). 확정 가능하면 증거, 아니면 LLM 힌트
- **E**: 판정 당시 관측 세션 수를 캐시에 기록하고, 2계층 문턱을 넘으면 자동 재분석
- **D**: LLM 출력에 `predictedPrerequisites` 추가. 상태 의존의 최종 그물

### 범위 밖

- 서버 간(cross-server) 의존 탐색
- `initialize`의 `instructions`, `prompts/list`, `annotations` 수집 (별도 계획)
- `merge.ts`의 판정 분기 변경
- 비활성화 자격 검사(`eligibility.ts`) 변경
- UI 신규 화면

### 계층별 담당 범위

| 의존의 종류 | 예시 | 담당 |
|---|---|---|
| 설명문에 툴 이름이 적힘 | `"call search_restaurants first"` | 1계층 (기존) |
| 불투명 값을 주고받고 이름 어간이 맞음 | `restaurant_id` ← `search_restaurants` | **A** |
| 불투명 값을 주고받는데 이름이 다름 | `venue_ref` ← `search_restaurants` | **B** |
| 상태로 이어지고 명사가 툴 이름에 있음 | `get_current_document` ← `open_document` | **F** (증거) |
| 상태로 이어지고 명사가 안 맞음 | `read_page` ← `navigate` | **F**(탐지) + **D**(귀속) |
| 시간이 지나 호출 기록이 쌓임 | 임의 | **E** |

### 4-3. `packages/core/src/store/store.ts` — `migrate()`

이 저장소는 번호 매긴 마이그레이션을 쓰지 않는다. `PRAGMA table_info`로 실제 컬럼을 조회해
없으면 추가하는 멱등 방식이다. 기존 블록 뒤에 두 블록을 추가한다.

```ts
  const bodyCols = new Set<string>();
  const bt = db.prepare('PRAGMA table_info(tool_definition_bodies)');
  while (bt.step()) bodyCols.add(bt.getAsObject().name as string);
  bt.free();
  // No backfill: a body written before this column has no outputSchema on record, and NULL is
  // exactly that fact. Writing '' would make the B tier read it as "publishes an empty output".
  if (!bodyCols.has('output_schema_json')) {
    db.exec('ALTER TABLE tool_definition_bodies ADD COLUMN output_schema_json TEXT');
  }

  const analysisCols = new Set<string>();
  const at = db.prepare('PRAGMA table_info(dependency_analyses)');
  while (at.step()) analysisCols.add(at.getAsObject().name as string);
  at.free();
  // Default 0 is the truthful value for a pre-existing row: the verdict was reached without
  // knowing the session count, which is indistinguishable from having observed none.
  // It also makes every stored row eligible for the reanalysis trigger exactly once.
  if (!analysisCols.has('observed_session_count')) {
    db.exec('ALTER TABLE dependency_analyses ADD COLUMN observed_session_count INTEGER NOT NULL DEFAULT 0');
  }
```

```ts
  /**
   * Distinct sessions in which this server's tools were called, within the given window.
   * Errors are counted: a session that only produced failures still proves the server was reachable
   * and exercised, which is what the call-chain tier needs to become meaningful.
```

### 4-5. `packages/core/src/scanner/serverIdentity.ts`

```ts
export interface RawToolBody {
  toolName: string;
  description?: string | null;
  inputSchema: unknown;
  outputSchema?: unknown;
}

export function computeDefinitionSetHash(
  serverName: string,
  bodies: readonly RawToolBody[],
): string {
  const tools = bodies
    .map((body) => ({
      toolName: body.toolName,
      description: body.description ?? null,
      inputSchema: canonicalize(body.inputSchema),
      outputSchema: body.outputSchema === undefined ? null : canonicalize(body.outputSchema),
    }))
    .sort((a, b) => a.toolName.localeCompare(b.toolName));
  return sha256(JSON.stringify({ serverName, tools }));
}

export function toolToRawBody(tool: Tool): RawToolBody {
  return {
    toolName: tool.name,
    description: tool.description ?? null,
    inputSchema: tool.inputSchema ?? {},
    outputSchema: (tool as { outputSchema?: unknown }).outputSchema,
  };
}
```

`outputSchema`를 해시에 넣는 것은 **의도된 부작용**이다. 해시가 바뀌면
`dependency_analyses`의 기존 캐시가 전부 미스가 되어 재분석이 강제된다.
새 계층이 반영되지 않은 낡은 판정이 남는 것을 이 한 줄이 막는다.

## 5. 계층별 사양

### 5-1. A + B — `packages/core/src/dependency/schemaFlow.ts` (신규)

#### 공개 시그니처

```ts
export function findSchemaFlowDependencies(
  bodies: readonly ToolDefinitionBody[],
): DependencyEvidence[];
```

반환 타입은 기존 `DependencyEvidence`를 그대로 쓴다. `staticRefs`·`callChains`와 같은
형태여야 `merge.ts`의 `blockers`에 그대로 합류한다.

#### 판정 규칙 (전량)

**1단계. 불투명 필드 골라내기**

소비자 후보 툴 B의 `inputSchema.required`에 있는 필드만 본다. 선택 입력은 없어도
동작하므로 의존의 근거가 못 된다.

```ts
/** Suffixes that name a value produced elsewhere rather than authored by a person. */
const OPAQUE_SUFFIX_RE = /(^|_)(id|ids|uuid|guid|key|keys|ref|refs|handle|token|cursor|slug)$/;

/**
 * Words that make an opaque-looking name a user-supplied secret instead of a tool output.
 * api_key and access_token match OPAQUE_SUFFIX_RE but nothing in the server produces them.
 */
const SECRET_HINT_RE = /(^|_)(api|secret|password|passwd|auth|bearer|access|refresh|client|private|public|license)(_|$)/;

/**
 * Formats a person can type. A field carrying one is authorable, so it is not an opaque handle.
 * uuid is deliberately absent: a uuid is the most opaque handle there is.
 */
const AUTHORABLE_FORMATS = new Set([
  'date', 'date-time', 'time', 'duration', 'email', 'idn-email',
  'hostname', 'idn-hostname', 'ipv4', 'ipv6', 'uri', 'url', 'iri', 'regex',
]);
```

필드가 불투명하려면 **아래를 모두** 만족해야 한다.

1. 정규화한 이름이 `OPAQUE_SUFFIX_RE`에 걸린다
2. 정규화한 이름이 `SECRET_HINT_RE`에 **안 걸린다**
3. `type`이 없거나 `'string' | 'integer' | 'number'` 중 하나다
4. `enum`이 없다 (열거값이면 사용자가 고를 수 있다)
5. `format`이 없거나 `AUTHORABLE_FORMATS`에 없다
6. `default`가 없다 (기본값이 있으면 안 줘도 동작한다)

이름 정규화는 camelCase를 snake_case로 펴고 소문자화한다.

```ts
function normalizeName(value: string): string {
  return value
    .replace(/([a-z0-9])([A-Z])/g, '$1_$2')
    .replace(/[^A-Za-z0-9]+/g, '_')
    .toLowerCase()
    .replace(/^_+|_+$/g, '');
}
```

**2단계. 생산자 후보 찾기**

같은 서버의 다른 툴 A마다 두 방법을 순서대로 시도한다.

*방법 1 (B안, 정확)* — A의 `outputSchemaJson`이 `null`이 아니면, 그 스키마의 모든
`properties` 키를 깊이 제한 없이 수집해 정규화한 집합을 만든다. `items.properties`도
따라 들어간다. 필드 이름이 그 집합에 있으면 A는 생산자다. 증거 문자열은
`schema-flow:output:<B>:<field>`.

*방법 2 (A안, 추측)* — A에 `outputSchema`가 없을 때만. 필드 이름에서 매칭된 접미사를
떼어 어간을 만든다. 어간이 빈 문자열이면 (`id`, `cursor`처럼 접미사만으로 된 이름)
**이 방법을 포기한다.** 어간 없이 매칭하면 `id` 하나가 서버의 모든 툴에 걸린다.

```ts
/** 'restaurant_id' -> 'restaurant'. Returns '' when the name is nothing but the suffix. */
function stemOf(normalizedField: string): string {
  return normalizedField.replace(OPAQUE_SUFFIX_RE, '');
}
```

어간이 A의 정규화된 툴 이름 또는 정규화된 설명문에 단어 경계로 나타나면 A는 후보다.
단복수는 허용한다. 증거 문자열은 `schema-flow:stem:<B>:<field>`.

```ts
function mentionsStem(stem: string, body: ToolDefinitionBody): boolean {
  const haystack = `${normalizeName(body.toolName)} ${normalizeName(body.description ?? '')}`;
  return new RegExp(`(^|_|\\s)${escapeRegex(stem)}(e?s)?($|_|\\s)`).test(haystack);
}
```

**3단계. 소비자 제외**

같은 필드를 **자기도 `required`로 요구하는 툴은 생산자에서 제외**한다.
`book_reservation`과 `cancel_reservation`이 둘 다 `restaurant_id`를 받으면
둘 다 소비자이지 생산자가 아니다. 이 규칙이 없으면 두 툴이 서로를 의존으로 지목한다.

**4단계. 후보 수로 판정**

| 생산자 후보 수 | 처리 | 근거 |
|---|---|---|
| 0 | 증거 없음 | 서버 밖에서 오는 값이거나 사용자가 아는 값이다 |
| **1** | **증거 생성** | 그 하나를 끄면 B가 값을 구할 방법이 없다 |
| 2 이상 | 증거 없음 | 하나를 꺼도 나머지가 남는다. 여기서 전부 막으면 오탐이 되어 절감 기회를 잃는다 |

방법 1로 찾은 후보가 하나라도 있으면 방법 2의 후보는 **버린다.** 정확한 대조가
추측을 이긴다. 둘을 합치면 `outputSchema`가 있는 서버에서 어간 오탐이 섞인다.

```ts
const DEICTIC_RE = /\b(current|currently|active|already[ -]open|this (page|session|document|file|window|tab|context|conversation)|the (open|opened|loaded|selected|focused|active) [a-z]+|previously (opened|selected|loaded|used)|last (opened|selected|used)|in progress)\b/i;
```

#### 생산자 귀속 (가능할 때만)

지시 표현 뒤의 명사를 뽑는다.

```ts
/** "the current page" -> "page". First capture only; a second deictic phrase is ignored. */
const STATE_NOUN_RE = /\b(?:current|currently|active|open|opened|loaded|selected|focused|this)\s+([a-z][a-z0-9_-]*)/i;
```

명사를 정규화하고 복수형 `s`를 뗀다. 그다음 같은 서버에서 생산자 후보를 찾는다.

1. 자기 자신이 상태 소비자가 **아니다**
2. `required` 입력이 하나 이상 있다 (밖에서 상태를 세울 수 있어야 한다)
3. 정규화된 툴 이름에 그 명사가 단어 경계로 들어 있다

후보가 **정확히 하나**일 때만 증거를 만든다. 증거 문자열은 `state-flow:<B>:<noun>`.

### 5-3. E — `packages/core/src/dependency/reanalysisTrigger.ts` (신규)

#### 상수의 출처

`callChains.ts`가 문턱값 `3`을 리터럴로 쓰고 있다. 이것을 상수로 올려 재사용한다.
**같은 태스크가 두 파일을 함께 소유한다.**

```ts
// packages/core/src/dependency/callChains.ts
/**
 * Minimum number of sessions in which A preceded B before the pair counts as a signal.
 * Below this the ordering is anecdote, not pattern. The reanalysis trigger reuses this value:
 * re-running the analysis is only worth its cost once this tier can produce a signal at all.
 */
export const CALL_CHAIN_MIN_SESSIONS = 3;
```

`findCallChainDependencies` 안의 `before >= 3`을 `before >= CALL_CHAIN_MIN_SESSIONS`로 바꾼다.
**다른 동작 변경은 없다.** 0.8 비율과 `bWithoutA < 2`는 그대로다.

#### 트리거 (전량)

```ts
import { CALL_CHAIN_MIN_SESSIONS } from './callChains.js';

export interface ReanalysisTriggerInput {
  /** observedSessionCount stored on the cached verdict. */
  storedSessionCount: number;
  /** Distinct sessions for this server right now, same 90-day window. */
  currentSessionCount: number;
}

/**
 * True when a cached verdict was reached before the call-chain tier could say anything and enough
 * sessions have since accumulated for it to speak.
 *
 * Fires at most once per server: after the rerun stores a count at or above the threshold, the
 * left-hand condition is false forever. Without that property a busy server would be re-analyzed
 * on every activation and spend the user's tokens each time.
 */
export function needsCallChainReanalysis(input: ReanalysisTriggerInput): boolean {
  return input.storedSessionCount < CALL_CHAIN_MIN_SESSIONS
    && input.currentSessionCount >= CALL_CHAIN_MIN_SESSIONS;
}
```

```ts
/** {toolName: B, requires: [A]} means A is needed by B, so the evidence lands on A. */
function prerequisiteEvidence(
  serverName: string,
  prerequisites: readonly PredictedPrerequisite[],
): DependencyEvidence[] {
  const byTool = new Map<string, DependencyEvidence>();
  for (const entry of prerequisites)
    for (const required of entry.requires) {
      const current = byTool.get(required)
        ?? { serverName, toolName: required, dependedOnBy: [], evidence: [] };
      if (!current.dependedOnBy.includes(entry.toolName)) current.dependedOnBy.push(entry.toolName);
      const reason = `llm-prereq:${entry.toolName}`;
      if (!current.evidence.includes(reason)) current.evidence.push(reason);
      byTool.set(required, current);
    }
  return [...byTool.values()].map((row) => ({
    ...row,
    dependedOnBy: row.dependedOnBy.sort(),
    evidence: row.evidence.sort(),
  })).sort((a, b) => a.toolName.localeCompare(b.toolName));
}
```

## 10. 남는 위험

이 계획으로도 못 잡는 것을 명시해 둔다.

**시간적 사각.** `rollback_deployment`, `restore_from_backup`처럼 장애 때만 쓰는 툴은
정의를 봐도 호출 기록을 봐도 "안 쓰임"으로 나온다. 어떤 정적 분석으로도 못 잡는다.
현재 `eligibility.ts`에 관측 기간 조건이 없으므로, 이 위험은 **끄기 전 확인 다이얼로그와
원클릭 복구**가 감당한다. 의도된 선택이다.

**서버 간 의존.** 범위 밖으로 결정했다. `github/search_issues` → `linear/create_task`
같은 흐름은 여전히 안 보인다.

**서버가 협조하지 않는 경우.** 설명문이 `"Read the page."`처럼 지시 표현 없이 짧으면
F가 탐지 못 한다. D가 마지막 그물이지만 확률적이다.

### 오류 방향의 비대칭

새 계층 셋 다 **의심스러우면 못 끄는 쪽**으로 기운다.

- 잘못 `Review required` → 못 끄는 도구가 생긴다. 손해는 절감 기회 상실이다.
- 잘못 `Independent` → 워크플로우가 깨진다. 손해는 신뢰다.

"생산자 후보가 2개 이상이면 증거를 안 만든다" 같은 규칙은 이 비대칭을 의식적으로
조정한 지점이다. 규칙을 손볼 때 이 방향이 유지되는지 먼저 확인한다.
