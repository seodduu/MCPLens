## 결함 1. 자동 분석 동의 모달이 영영 안 뜬다

`packages/extension/src/setupCommands.ts:45`

```ts
if (config.inspect<string>('autoScan')?.globalValue !== undefined) return;
```

이 함수(`askAutomationConsentOnce`)는 "자동 스캔 + 자동 분석" 동의를 온보딩 마지막 단계에서
한 번 받고, 답을 `autoScan`과 `autoAnalyze` 두 설정에 쓴다. 그런데 "이미 물어봤나"를
`autoScan`으로 판정한다.

`autoScan`은 이 함수 말고 다른 곳에서도 써진다. `packages/extension/src/autoScan.ts:171`,
자동 스캔 프롬프트에서 "Scan"을 누르면:

```ts
await config.update('autoScan', 'always', vscode.ConfigurationTarget.Global);
```

여기서는 `autoAnalyze`를 쓰지 않는다. 같은 파일 174행의 "Don't ask again"(`'never'`)도 같다.

그래서 **스캔 프롬프트를 온보딩 마지막 단계보다 먼저 만난 사용자**는 `autoScan`이 이미
기록된 상태가 되고, 마지막 단계의 모달은 45행에서 조용히 early return 한다. 동의를 물어본
적이 없는데 물어봤다고 판정하며, `autoAnalyze`는 미기록으로 남아 기본값 `false`가 된다.

그 결과 `packages/extension/src/extension.ts:553`의 게이트가 항상 닫힌다.

```ts
if (!vscode.workspace.getConfiguration('mcpLens').get<boolean>('autoAnalyze', false)) return;
```

사용자 설정이 정확히 이 상태였다.

### 고치는 방향

두 갈래로 고친다. 하나만으로는 부족하다.

**1a. 판정 키를 `autoAnalyze`로 바꾼다.** `autoAnalyze`는 이 모달만 쓴다. 그러니 이 설정이
기록됐는지가 "물어봤는가"의 정직한 기록이다. 신규 사용자의 순서 문제가 사라진다.

**1b. 자동 분석 직전에 미기록이면 그 자리에서 한 번 묻는다.** 1a만으로는 이미 온보딩
마지막 단계를 지나온 기존 사용자가 복구되지 않는다(그 커맨드를 다시 실행할 계기가 없다).
`analyzeAfterScan`에서 `autoAnalyze`가 **미기록**이면 같은 동의 모달을 띄우고 답을 기록한 뒤
그에 따라 진행한다. 명시적으로 `false`가 기록돼 있으면 묻지 않고 조용히 반환한다.

이 자리가 정직한 이유: 토큰을 쓰기 직전, 새 서버가 방금 스캔된 시점이다. 첫 실행은
`decideScanAction`이 `neverScanned`로 skip하므로 여기 도달하지 않고, 수동 스캔은 분석으로
체인하지 않는다. 즉 이 모달은 "새 서버가 자동 스캔된" 경로에서만 뜬다.

## 결함 2. codex의 url 기반 MCP 서버를 통째로 버린다

`packages/core/src/scanner/sources.ts:89`

```ts
if (typeof s?.command === 'string') {
  specs.push({ name, command: s.command, args: s.args ?? [], env: s.env });
}
// Entries with neither a command nor enabled=false (transport undeterminable) are ignored on purpose.
// Unlike the unknown handling in collectServerSpecs, codex has no http url field, so the skip reason differs and it is dropped with no contract.
```

주석의 "codex has no http url field"가 사실이 아니다. codex는 remote(streamable HTTP) MCP를
`url =`로 받는다. 사용자 설정이 반증이다.

```toml
[mcp_servers.notion]
url = "https://mcp.notion.com/mcp"
```

`McpServerSpec`(`packages/core/src/scanner/configs.ts`)은 이미 `url`과 `headers`를 갖고 있고
`specTransport`가 `url`만 있으면 `'http'`를 돌려준다. 즉 스캐너 쪽 계약은 이미 준비돼 있고
codex 파서만 안 채운다.

### 고치는 방향

`collectCodex`에서 `command`가 없고 `url`이 문자열이면 http 스펙으로 받는다. codex가 원격
서버에 붙일 때 쓰는 부속 필드도 함께 옮긴다.

- `http_headers`: 헤더 이름 -> 값 테이블. 그대로 `headers`에 넣는다.
- `bearer_token_env_var`: 값이 환경변수 **이름**이다. 해당 환경변수가 있으면
  `Authorization: Bearer <값>`을 헤더에 더한다. 없으면 헤더를 만들지 않는다(빈 Bearer를
  보내면 서버가 401 대신 400을 주는 쪽이 많아 원인 파악이 더 어려워진다).
- `http_headers`에 이미 `Authorization`이 있으면 그쪽을 이긴다(사용자가 직접 쓴 값이므로).

`command`와 `url`이 둘 다 없는 항목은 지금처럼 버리되, 주석의 거짓 단언을 지운다.

## 결함 3. 동명 서버 충돌이 숫자에 반영되지 않는다

애초 진단은 "서버 식별에 클라이언트 차원이 없다"였다. 코드를 읽어보니 **그것은 의도된
설계이고 감지 장치도 이미 있다.** 정정한다.

`sources.ts:168`에서 이름이 겹치면 우선순위 앞 소스가 이긴다
(claude-user > claude-project > codex > gemini). 그리고 `markEndpointConflicts`(189행)가
같은 이름에 서로 다른 `endpointHash`가 있으면 `conflictState: 'conflict'`로 표시한다.
`extension.ts:365`는 이 상태를 툴 행에 `Identity conflict`로 띄운다.
`globalActionCommand.ts`는 충돌 서버의 전역 토글을 막는다.

사용자의 notion은 claude-code와 gemini-cli 양쪽에 있는데 `endpoint_hash`가
`1cbd18bf...`로 동일하고 `conflict_state`는 `clear`다. 실제로 같은 원격 서버
(`https://mcp.notion.com/mcp`)이므로 하나로 합쳐 재는 것이 옳다. 결함 2를 고치면 codex의
notion도 같은 해시로 붙어 정상 귀속된다. **즉 이번 증상에 한해 동명 문제는 원인이 아니다.**

남는 진짜 결함은 다음이다. **엔드포인트가 서로 다른 동명 서버일 때, 스캔은 우선순위 앞
클라이언트의 서버 하나만 재는데 그 토큰 수가 다른 클라이언트 몫으로도 집계된다.**

토큰과 절감액을 그대로 더한다. 이것은 CLAUDE.md가 금지하는 "틀리면 결론이 뒤집히는 숫자"다.

### 고치는 방향

PK에 클라이언트를 넣는 재배선은 하지 않는다. 스키마 계약(`schema.sql`, `types.ts`)과 모든
조인·해시·대시보드를 건드리는 변경인데, 얻는 것에 비해 파급이 지나치게 크다. 대신 **충돌한
서버를 숫자에서 빼고 뺐다는 사실을 드러낸다.**

- `buildReport`가 충돌 서버 이름 집합을 입력으로 받는다. 그 서버의 행은 절감 후보
  집계(`actToolCount`/`candidateToolCount`/`actPerSessionTokens`/`candidatePerSessionTokens`)에서
  제외한다. 툴 목록에는 남기되 상태를 충돌로 표시한다.
- 제외한 서버 이름을 리포트 모델에 `conflictedServers`로 실어 보내 리포트 본문과 상태바
  툴팁이 "N개 서버는 이름 충돌로 집계에서 제외됨"을 말하게 한다. 조용히 빼면 결함 2와 같은

`automationConsent.ts`에 모달 제기 자체를 함수로 빼서 두 호출자가 공유한다. 문구가 갈리면

```ts
/**
 * Raises the automation consent modal and writes the answer, unless it was already answered.
 * Returns the value of autoAnalyze afterwards, so the caller can act on the fresh answer without
 * re-reading the setting (the update is async and a stale read would skip the analysis the user just approved).
 */
export async function ensureAutomationConsent(
  config: {
    inspect: (key: string) => { globalValue?: unknown } | undefined;
    update: (key: string, value: unknown, target: unknown) => Thenable<void>;
  },
  ask: () => Thenable<string | undefined>,
  globalTarget: unknown,
): Promise<boolean>;
```

사양: `inspect('autoAnalyze')?.globalValue`가 `undefined`가 아니면 묻지 않고 그 값을

`automationSettings`로 변환해 `autoScan`과 `autoAnalyze`를 모두 `globalTarget`에 쓰고
`autoAnalyze` 값을 돌려준다.

`extension.ts`의 `analyzeAfterScan`:

```ts
const analyzeAfterScan = async (): Promise<void> => {
  const config = vscode.workspace.getConfiguration('mcpLens');
  // A user who answered the automatic scan prompt before finishing onboarding never saw the
  // automation consent modal, so autoAnalyze stays unwritten and analysis would be skipped in
  // silence. Ask here instead: a new server has just been scanned, which is the moment the tokens
  // would be spent. An explicit false is respected without asking again.
  const consented = await ensureAutomationConsent(
    config,
    () => vscode.window.showInformationMessage(
      AUTOMATION_PROMPT_TITLE, { modal: true, detail: AUTOMATION_PROMPT_DETAIL },
      AUTOMATION_ACCEPT_LABEL, AUTOMATION_SCAN_ONLY_LABEL),
    vscode.ConfigurationTarget.Global);
  if (!consented) return;
  await analysisCoordinator.analyze([], { auto: true });
};
```

```ts
/**
 * Headers for a codex remote server. bearer_token_env_var holds the NAME of an environment
 * variable, not the token. When that variable is unset no Authorization header is produced: sending
 * an empty Bearer draws a 400 from most servers, which is harder to trace back than the 401 that a
 * missing header gives. An Authorization written by hand in http_headers wins, because it is the
 * user's own explicit value.
 */
function codexHttpHeaders(s: any): Record<string, string> | undefined {
  const headers: Record<string, string> = {};
  const envVar = s?.bearer_token_env_var;
  if (typeof envVar === 'string') {
    const token = process.env[envVar];
    if (token) headers.Authorization = `Bearer ${token}`;
  }
  const written = s?.http_headers;
  if (written && typeof written === 'object') {
    for (const [key, value] of Object.entries(written)) {
      if (typeof value === 'string') headers[key] = value;
    }
  }
  return Object.keys(headers).length > 0 ? headers : undefined;
}
```

```ts
/**
 * Names of servers whose identity conflicts across clients (two clients define the same name with a
 * different endpoint). Only one of them is actually scanned, so its token figure does not describe
 * the other client's server. Counting it as a saving would state a number that is not true, so these
```

`rollupClient`에서 행을 집계할 때, `conflictedServers`에 든 `serverName`의 행은
`actToolCount`, `candidateToolCount`, `actPerSessionTokens`, `candidatePerSessionTokens`

```ts
/** Servers left out of the waste totals because of an identity conflict. Empty when there are none. */

```

`markdown.ts`는 `conflictedServers`가 비어 있지 않으면 총계 바로 아래에 한 줄을 넣는다.
문구(사용자에게 보이는 면이므로 영어):

```

```

`extension.ts`의 `buildReport` 호출부는 충돌 서버 집합을 만들어 넘긴다.

```ts
// One scan measures one server per name, so a name claimed by two clients with different endpoints
// cannot have both measured. Its tokens are therefore not evidence about either client, and it is
// kept out of the waste figure on the status bar.
const conflictedServers = new Set(
  store!.serverIdentities()
    .filter((identity) => identity.conflictState !== 'clear')
    .map((identity) => identity.serverName));
```
