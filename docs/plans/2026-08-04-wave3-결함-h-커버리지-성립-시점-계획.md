# Wave 3 결함 H 보정 구현 계획 — 커버리지 성립 시점까지 반영한다

결함 F 보정 이후 실기기 검증에서, **훅을 새로 설치한 사용자가 과거 로그 이력 때문에 곧바로
`degraded`로 시작하고 codex 세션을 한 번 끝내야만 빠져나오는** 문제가 드러났다.

기점 커밋은 이 계획서를 커밋한 시점의 HEAD다.

## 관측된 사실

결함 G 보정으로 codex 훅이 켜진 직후, 실기기 codex 관측을 실측했다.

| 항목 | 값 |
|---|---|
| 툴 단계 hook 최초 관측 | `2026-08-04T11:58:47.854Z` |
| log 완료(`tool-after`/`tool-failure`) 총계 | 116건 |
| 그중 **커버리지 성립 이전** | **116건 (전부)** |
| 커버리지 성립 이후 | 0건 |
| 계산된 건강도 | `degraded`, 연속 불일치 116 |

116건은 훅이 설치되기 전에 일어난 호출이다. **훅이 존재할 수가 없었으므로 짝이 없는 것이
당연하다.** 그런데 현재 로직은 이를 "수집기 장애"로 센다.

## 원인: 결함 F가 "언제부터"를 보지 않았다

`collectionHealth.ts:143`의 승격 조건은 이렇다.

```ts
if (toolHookCoverageObserved && consecutiveMisses >= MISSES_TO_DEGRADE) degraded = true;
```

`toolHookCoverageObserved`는 **"툴 단계 hook이 한 번이라도 있었나"**만 본다. 그 hook보다
**앞선** log 완료까지 승격 근거로 삼는다. 결함 F가 고친 오류("hook 없는 운용을 장애로 오판")와
같은 종류인데, F는 존재 여부만 게이트하고 시점은 게이트하지 않았다.

결과적으로 훅을 새로 켠 모든 사용자가 과거 이력만큼의 miss를 안고 시작한다. 빠져나오려면
`MATCHES_TO_RECOVER`(2건)를 채워야 하고, 매치는 log 완료가 있어야 성립한다.

## 왜 세션 재시작이 필요했는가

매치는 **log `tool-after`** 관측에서만 만들어진다(`:112-116`의 루프가 log 완료만 순회한다).
그런데 codex는 rollout 로그를 **세션 종료 시에만 flush**한다. 실측 데이터가 이를 그대로 보여준다.

| 시각 | 세션 | hook | log |
|---|---|---|---|
| 12:01:25 (`native:de50da5`) | 진행 중 | `tool-before` ✓ `tool-after` ✓ | **없음** |
| 11:59:18 (`native:e484993`) | 종료됨 | `tool-before` ✓ `tool-after` ✓ | `tool-after` ✓ → 매치 |

그래서 진행 중인 세션에서 아무리 MCP 호출을 해도 매치가 안 만들어지고, 세션을 끝내야 회복됐다.

**이 flush 시점은 codex의 동작이라 우리가 바꿀 수 없다.** 다만 애초에 `degraded`가 되지 않으면
회복을 기다릴 일 자체가 없다. 이 계획은 그쪽을 고친다.

## 설계 판단: 승격 근거를 커버리지 성립 이후로 제한한다

`degraded`가 뜻해야 하는 것은 **"돌고 있던 hook 수집기가 멈췄다"**는 회귀 신호다(결함 F에서
정한 정의). 커버리지가 성립하기 **이전**의 log 완료는 그 정의상 회귀의 증거가 될 수 없다.
그때는 수집기가 애초에 붙어 있지 않았다.

따라서 miss가 `degraded`를 만들려면 두 조건을 모두 만족해야 한다.

1. 툴 단계 hook 커버리지가 성립한 적 있다 (결함 F에서 도입)
2. **그 miss가 커버리지 성립 시점 이후에 일어났다** (이번 보정)

### miss 계수는 여전히 건드리지 않는다

`consecutiveMisses`는 "짝을 못 찾고 유예를 넘긴 log 완료"라는 뜻 그대로 둔다. 결함 F에서
정한 이유가 그대로 유효하다.

1. 기존 사양이 hook 0건 상태에서 `consecutiveMisses: 1`을 요구한다
   (`matures an unmatched log observation at the exact grace boundary`).
2. 진단 값으로서의 miss 계수와 "수집기가 고장났다"는 판정은 다른 층위다.

### 남는 한계를 명시한다

이 보정 뒤에도 codex는 **진짜 훅 회귀를 한 세션 늦게** 알린다. 회귀를 증명하는 log 완료가
세션 종료 시에만 도착하기 때문이다. 건강도는 실시간 경보가 아니라 수집 품질 지표이고,
호출 수·토큰 누적은 hook 관측만으로 실시간 반영되므로(`observations.ts`의 hook 단독 경로)
이 지연은 감수한다.

## 변경: `packages/core/src/health/collectionHealth.ts`

### 변경 1: 커버리지 성립 시점을 계산한다

`toolHookCoverageObserved`를 계산하는 자리(`:106-108`)를 아래로 대체한다.

```ts
  // 툴 단계 hook 커버리지가 성립한 시점. hookTimesByKey는 HOOK_COVERAGE_PHASES만 담으므로
  // 이 맵이 비어 있다는 것은 툴 단계 hook을 한 번도 못 봤다는 뜻이다.
  // 최솟값을 쓰는 이유: 그 시각부터가 "hook이 이 호출을 봤어야 하는" 구간이다.
  const toolHookTimes = [...hookTimesByKey.values()].flat();
  const coverageSince = toolHookTimes.length === 0 ? null : Math.min(...toolHookTimes);
  const toolHookCoverageObserved = coverageSince !== null;
```

`observations`는 `compareObservations`로 정렬돼 있지만 `hookTimesByKey`의 값 배열은 삽입
순서이므로 `Math.min`으로 명시적으로 구한다. 정렬에 의존하지 않는다.

### 변경 2: 승격 조건에 시점을 더한다

`:143`을 아래로 대체한다.

```ts
      // 툴 단계 hook을 한 번도 못 본 클라이언트에서 miss는 수집기 장애의 증거가 아니다.
      // hook 없이 로그만으로 운용하는 정상 형태이며, 그것은 log-only로 표기된다.
      //
      // 커버리지가 성립하기 이전의 log 완료도 마찬가지다. 그때는 수집기가 붙어 있지
      // 않았으므로 짝이 없는 것이 당연하고, "돌던 수집기가 멈췄다"는 회귀의 증거가 될 수
      // 없다. 이 시점 조건이 없으면 훅을 새로 켠 사용자가 과거 이력만큼의 miss를 안고
      // degraded로 시작하고, 매치를 만들어 빠져나올 때까지 전역 액션이 막힌다.
      // (실측: 훅 설치 직후 codex의 miss 116건이 전부 커버리지 성립 이전이었다.)
      if (coverageSince !== null
        && outcome.time >= coverageSince
        && consecutiveMisses >= MISSES_TO_DEGRADE) degraded = true;
```

`toolHookCoverageObserved`는 스냅샷 필드로 계속 반환하므로 변수는 남긴다.

다른 변경은 없다. 회복 조건(`MATCHES_TO_RECOVER`), miss 계수, 라벨 판정은 그대로다.

## 이 계획이 다루지 않는 것

**codex 로그의 flush 시점.** 세션 종료 시에만 rollout이 기록되는 것은 codex 동작이라 바꿀 수
없다. 이 보정 뒤에도 진짜 훅 회귀 감지는 한 세션 늦다. 건강도는 실시간 경보가 아니고, 호출
수·토큰 누적은 hook 단독으로 실시간 반영되므로 감수한다.

**`eligibility.ts`.** `log-only`와 `healthy`를 이미 정상으로 인정한다. 고칠 것이 없다.

  계획서의 "변경 1"과 "변경 2", 그리고 "테스트" 절의 새 테스트 3건을 구현한다. 소유 파일은 packages/core/src/health/collectionHealth.ts와 packages/core/test/health/collectionHealth.test.ts뿐이다. packages/core/src/types.ts, packages/core/src/store/schema.sql, packages/core/src/dependency/eligibility.ts, packages/core/test/e2e/hook-health.test.ts는 수정하지 않는다. 계획서의 "테스트" 절 표에 기존 테스트 21건이 왜 안 바뀌는지 이유가 전부 적혀 있다. 기존 테스트의 기존 단언은 하나도 고치지 않는다. 하나라도 실패하면 구현이 계획과 다르다는 뜻이므로 임의로 테스트를 바꾸지 말고 원인을 보고한다. 유닛테스트는 인메모리 데이터만 쓴다. 실기기 자원은 건드리지 않는다. 끝나면 `npm run build`, `npm test`, `npx tsc --noEmit -p packages/core/tsconfig.json`, `npx tsc --noEmit -p packages/extension/tsconfig.json`을 실행하고 결과를 보고한다. 커밋·merge·push는 하지 않는다.

자식이 끝나면 당신이 검증한다. `git diff --stat`으로 소유 파일 밖 변경이 0건인지 확인한다. `git diff packages/core/test/health/collectionHealth.test.ts`를 보고 기존 단언이 바뀌지 않고 새 테스트만 추가됐는지 직접 확인한다. `npm test` 전량 통과, tsc 양쪽 통과를 확인한다. 하나라도 어긋나면 고치게 하고 다시 검증한다.

전부 통과하면 한국어로 원자적 커밋 하나를 만든다. 커밋 메시지는 실측(훅 설치 직후 miss 116건이 전부 커버리지 성립 이전이었다), degraded 승격에 시점 조건을 더한 근거, miss 계수는 왜 그대로 뒀는지, codex 로그 flush 지연은 왜 범위 밖인지를 담는다. push는 하지 않는다.

마지막에 사용자에게 브랜치명, 커밋 SHA, 검증 결과, 남은 위험(진짜 훅 회귀 감지가 한 세션 늦다)을 보고한다.
