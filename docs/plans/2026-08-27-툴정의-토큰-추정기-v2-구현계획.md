# 툴 정의 토큰 추정기 v2 구현 계획

작성일: 2026-08-27. 기점 커밋: `2d1f613`(main).
근거 데이터: `docs/plans/assets/2026-08-27-보정-근거-day-01.json`.
관련 설계: `docs/designs/2026-08-26-일일-배치-before-after-측정-설계.md` 12절.

Lens가 "이 서버를 끄면 N토큰이 남는다"고 말할 때의 N이 평균 36.8% 틀렸다. 이 계획은 그 N을
하네스가 실제로 싣는 양에 맞춘다. 파일럿 1일차 실측 10서버 기준으로 평균 오차 36.8%를 7.4%로
줄이는 것이 목표다.

## 1. 목표·비범위·완료 조건

### 목표

- 스캐너가 저장하는 서버별 정의 토큰 합계가 실측값과 평균 10% 이내로 맞는다.
- 서버 `instructions`가 컨텍스트 비용으로 잡히고, **서버를 끄는 것과 툴만 거르는 것의 절감이
  다르게** 계산된다. 툴만 걸러도 `instructions`는 남는다.
- 모든 추정치에 `estimatorVersion`이 스냅샷으로 붙어, 버전이 다른 수치를 섞어 평균 내는 사고를
  막는다.

### 비범위

- 하네스가 왜 1.608배로 부풀리는지 규명하지 않는다. 이 계획은 그 배율을 측정값으로 다루고
  출처와 표본을 스냅샷으로 남긴다. 규명은 배치가 쌓인 뒤 별건이다.
- Codex·Gemini CLI용 배율을 따로 만들지 않는다. 실측이 Claude Code eager 하나뿐이다.
  같은 배율을 쓰되 `calibrationSource`에 그 사실을 적는다.
- 파일럿 장부(`pilot/**`)는 이 계획에서 건드리지 않는다. 브랜치가 다르고, 1일차 수치는 v1
  추정기로 찍힌 기록이라 그대로 둬야 한다. 파일럿 반영은 5절 후속 항목이다.
- 대시보드·확장 UI의 문구를 바꾸지 않는다. 숫자의 출처만 바뀐다.

### 완료 조건

- `npm test`가 녹색이고, 신규 테스트(6절) 전량이 통과한다.
- `npx tsc --noEmit -p packages/core/tsconfig.json`과
  `npx tsc --noEmit -p packages/extension/tsconfig.json`이 통과한다
  (extension은 `npm run build -w @mcp-lens/core` 선행).
- `packages/core/test/fixtures/calibration/day-01.json`의 10개 서버에 대해 v2 추정치의 평균
  절대오차가 10% 미만이라는 단언이 통과한다.
- 기존 DB를 열었을 때 마이그레이션이 새 컬럼을 추가하고, 재스캔 전까지 기존 행이 v1 값으로
  읽히며 `estimatorVersion`이 `v1`로 표시된다.

## 2. 무엇이 왜 틀렸나 (측정 근거)

1일차 실측은 12구성 차감법이다. `context(all10) − context(minus_k)`가 서버 k의 실제 무게다.

| 서버 | 툴 | v1 추정 | 실측 | v1 오차 | v2 추정 | v2 오차 |
|---|---|---|---|---|---|---|
| huggingface | 4 | 4,480 | 3,286 | 36% 과대 | 3,189 | 2.9% |
| awsknowledge | 5 | 1,836 | 3,160 | 42% 과소 | 3,012 | 4.7% |
| mslearn | 3 | 869 | 1,872 | 54% 과소 | 1,659 | 11.4% |
| context7 | 2 | 981 | 1,812 | 46% 과소 | 1,799 | 0.7% |
| deepwiki | 3 | 321 | 1,166 | 72% 과소 | 1,331 | 14.1% |
| cloudflare-docs | 2 | 388 | 486 | 20% 과소 | 428 | 11.9% |
| svelte | 4 | 1,220 | 1,845 | 34% 과소 | 1,893 | 2.6% |
| memory | 9 | 1,996 | 1,653 | 21% 과대 | 1,526 | 7.7% |
| filesystem | 14 | 2,352 | 2,949 | 20% 과소 | 2,790 | 5.4% |
| sequential-thinking | 1 | 948 | 1,227 | 23% 과소 | 1,384 | 12.8% |
| **평균 절대오차** | | | | **36.8%** | | **7.4%** |

원인이 셋이다.

**(a) `outputSchema`를 센다.** Anthropic Messages API의 tool 정의에는 `name`, `description`,
`input_schema`밖에 없다. 하네스가 보내지 않는 필드를 Lens가 세고 있다. 과대평가 두 건
(huggingface, memory)이 정확히 `outputSchema`를 많이 싣는 서버다.
현재 코드: `packages/core/src/scanner/scanner.ts`의 `definitionTokens` 계산.

**(b) 서버 `instructions`를 안 센다.** MCP `initialize` 응답의 `instructions`를 Claude Code는
시스템 프롬프트에 넣는다. Lens는 `tools/list`만 본다. 1일차 서버의 실측 `instructions` 토큰은
deepwiki 578, huggingface 361, mslearn 290, context7 126, svelte 50이고 나머지는 0이다.
deepwiki가 72% 과소평가된 이유가 이것이다. 정의 250토큰짜리 서버가 instructions로 578을 더 먹는다.

**(c) 남는 것은 일정한 배율이다.** (a)와 (b)를 고치면 10개 서버가 전부 같은 방향(과소)으로
정렬되고, 배율 하나로 맞는다. 최소제곱으로 `measured = a × base + b × toolCount`를 풀면
`a = 1.608`, `b = 12`가 나온다. 툴당 상수항 12는 사실상 0이므로 버리고 배율만 쓴다.
`mcp__server__tool` 접두사 가설은 이 결과로 기각된다. 접두사가 원인이면 툴 개수에 비례하는
상수항이 커야 하는데 그렇지 않다.

배율의 정체는 모른다. o200k_base 토크나이저와 Anthropic 토크나이저의 차이일 수도 있고,
하네스가 스키마를 다른 형태로 렌더링하는 것일 수도 있다. **이 계획은 그것을 측정값으로
다룬다.** 표본 10개, 출처 1일차, 평균 잔차 7.4%를 상수와 함께 코드에 적는다.

## 3. 공유 계약

세 파일이 동시에 바뀐다. 이 절이 유일한 진실이며 T1이 단독으로 소유한다.

### 3.1 `packages/core/src/types.ts`

```ts
/** Which estimator produced a token number. Rows written before the calibrated estimator read as 'v1'. */
export type EstimatorVersion = 'v1' | 'v2-2026-08-27';

export interface ToolDefinition {
  serverName: string;
  toolName: string;
  /**
   * What the client is expected to actually load for this tool, calibrated against measured
   * context weight (docs/plans/2026-08-27-툴정의-토큰-추정기-v2-구현계획.md section 2).
   * Every consumer that asks "how much does this tool cost" reads this field.
   */
  definitionTokens: number;
  /** The uncalibrated count: tokens of {name, description, inputSchema} under o200k_base. Kept for audit. */
  advertisedTokens: number;
  estimatorVersion: EstimatorVersion;
  scannedAt: string;
  firstScannedAt: string;
}

/**
 * Per-server context cost that no single tool owns: the `instructions` string from the
 * initialize response. Filtering individual tools does not remove it; removing the server does.
 */
export interface ServerContextOverhead {
  serverName: string;
  /** Calibrated, same factor as ToolDefinition.definitionTokens. 0 when the server publishes none. */
  instructionsTokens: number;
  /** null when the server publishes no instructions. Lets a rescan tell "unchanged" from "gone". */
  instructionsSha256: string | null;
  estimatorVersion: EstimatorVersion;
  scannedAt: string;
}
```

`ToolDefinitionBody`는 바꾸지 않는다. `output_schema_json`은 계속 저장한다. 의존성 판정(B 티어)이
그것을 읽고, 저장을 멈추면 그쪽이 깨진다. **바뀌는 것은 저장 여부가 아니라 토큰 계산에
포함하느냐다.**

### 3.2 `packages/core/src/store/schema.sql`

```sql
CREATE TABLE IF NOT EXISTS tool_definitions (
  server_name       TEXT NOT NULL,
  tool_name         TEXT NOT NULL,
  definition_tokens INTEGER NOT NULL,
  advertised_tokens INTEGER,
  estimator_version TEXT,
  scanned_at        TEXT NOT NULL,
  first_scanned_at  TEXT,
  PRIMARY KEY (server_name, tool_name)
);

CREATE TABLE IF NOT EXISTS server_context_overheads (
  server_name         TEXT PRIMARY KEY,
  instructions_tokens INTEGER NOT NULL,
  instructions_sha256 TEXT,
  estimator_version   TEXT NOT NULL,
  scanned_at          TEXT NOT NULL
);
```

`advertised_tokens`와 `estimator_version`은 NOT NULL이 아니다. 기존 행에 채울 진실이 없기
때문이다. 읽을 때 `estimator_version`이 NULL이면 `'v1'`으로 읽는다.

### 3.3 `packages/core/src/store/store.ts`의 `migrate()`

이 저장소는 번호 붙은 마이그레이션이 아니라 컬럼 검사식이다. 같은 패턴을 따른다.

```ts
  // 기존 tool_definitions 컬럼 검사 블록 안에 이어서
  if (!cols.has('advertised_tokens')) {
    // No backfill: a v1 row's definition_tokens included outputSchema and no calibration, so
    // there is no honest advertised value to write. NULL is exactly "we do not know".
    db.exec('ALTER TABLE tool_definitions ADD COLUMN advertised_tokens INTEGER');
  }
  if (!cols.has('estimator_version')) {
    db.exec('ALTER TABLE tool_definitions ADD COLUMN estimator_version TEXT');
    db.exec("UPDATE tool_definitions SET estimator_version = 'v1'");
  }
```

`server_context_overheads`는 새 테이블이므로 `schema.sql`의 `CREATE TABLE IF NOT EXISTS`가
처리한다. 마이그레이션 코드가 따로 필요 없다.

### 3.4 `packages/core/src/scanner/calibration.ts` (신규)

배율은 매직넘버다. 값과 출처를 같은 파일에 둔다.

```ts
export const ESTIMATOR_VERSION = 'v2-2026-08-27' as const;

/**
 * Measured on the daily-batch pilot, day-01 (2026-08-26, commit 599f9df): 10 servers, eager mode,
 * Claude Code, weight measured by 12-config subtraction on real sessions.
 *
 * measured ≈ FACTOR × (tokens of {name: "mcp__<server>__<tool>", description, inputSchema}
 *                      + tokens of the server's initialize instructions)
 *
 * Least squares over the 10 servers also fits a per-tool constant of 12 tokens, which is inside
 * the noise and is therefore dropped: the harness cost scales with content, not with tool count.
 * Mean absolute error after calibration: 7.4% (was 36.8% uncalibrated). Range 0.7% to 14.1%.
 * Evidence: docs/plans/assets/2026-08-27-보정-근거-day-01.json
 *
 * Only Claude Code in eager mode has been measured. Codex and Gemini CLI reuse this factor and
 * say so through calibrationSource, rather than pretending to a measurement that does not exist.
 */
export const HARNESS_FACTOR = 1.608;
export const CALIBRATION_SOURCE = 'claude-code-eager-pilot-day-01' as const;

/** Applies the harness factor. Rounds half up so a 0-token input stays 0. */
export function calibrate(rawTokens: number): number {
  return Math.round(rawTokens * HARNESS_FACTOR);
}
```

### 3.5 귀속 규칙 (판단이 갈리는 곳이라 규칙으로 못 박는다)

| 행동 | 절감 |
|---|---|
| 서버 전체를 끈다 | `Σ 그 서버 툴의 definitionTokens` + `instructionsTokens` |
| 그 서버의 툴 일부만 끈다 | `Σ 끄는 툴의 definitionTokens` (instructions는 남는다) |
| 그 서버의 툴 전부를 끄되 서버 연결은 유지한다 | `Σ 툴` (instructions는 남는다) |

세 번째 줄이 함정이다. 툴을 전부 거른 것과 서버를 끈 것은 절감이 다르며, 차이가 곧
`instructionsTokens`다. `filter-server` 추천이 `remove`보다 덜 절약된다는 사실이 리포트에
드러나야 한다.

## 5. 후속 (이 계획 밖)

- 파일럿 장부에 `estimatorVersion`을 기록하고 `--summary`가 버전이 다른 `errorRate`를 섞어
  평균 내지 않게 한다. 브랜치 `pilot/daily-batch` 몫이며, 2일차 실행(T7) 전에 넣는다.
- 배치가 쌓이면 `HARNESS_FACTOR`를 다시 적합한다. 표본이 10에서 늘어날 때마다 상수와
  주석의 오차 수치를 같이 갱신한다.
- 배율의 정체 규명. 하네스가 스키마를 어떤 형태로 렌더링하는지 확인되면 배율이 구조로
  바뀔 수 있다.

### 구현 뒤 확정된 후속 (2026-08-27, `f4aa8cf` 기준)

- **CLI 리포트와 대시보드는 서버 단위 `instructions` 귀속을 아직 안 쓴다.** 두 면은
  `buildMatrix` + `sessionSavings` 경로이고, `serverOverheads`를 실제로 소비하는 곳은
  `rollup.ts`의 `buildReport` 하나다. `EngineInput`에 필드를 넘겨봐야 수치가 한 자리도 안
  바뀌므로 배선하지 않았다. 툴 단위 토큰은 두 면 모두 재스캔 뒤 v2 값이다. 빠진 것은 서버
  단위 항목 하나다. 반영하려면 두 면을 `buildReport` 경로로 옮기거나 `sessionSavings`의
  `potentialTokens`가 `instructions`를 양변에 반영해야 하고, 둘 다 출력 형태를 건드리므로
  1절 비범위에 걸린다. 별도 태스크로 연다.
- **`node_modules` 심링크가 낡은 `packages/core`를 가리키면 타입체크가 거짓 녹색을 낸다.**
  worktree의 `node_modules`를 루트로 통째 심링크하면 `@mcp-lens/core`가 루트 저장소의
  `packages/core/dist`로 해소되어, 이 브랜치의 계약 변경을 cli·extension이 전혀 못 본다.
  머지 게이트에서 `readlink -f node_modules/@mcp-lens/core`가 그 worktree 안을 가리키는지
  확인한다. 이번 구현에서 실제로 이 착시가 났고, 바로잡은 뒤에야
  `packages/dashboard/test/server.test.ts`의 픽스처 결함이 드러났다.

## 6. 테스트 케이스와 단언 (전량)

**T1** (`packages/core/test/store/estimatorV2.test.ts` 신규. 기존 store 테스트 파일은 다른 주제를 담고 있다)

- `round-trips advertisedTokens and estimatorVersion`: 저장 후 조회한 행의 두 필드가 저장값과
  같다.
- `reads a pre-migration row as estimator version v1`: `advertised_tokens`, `estimator_version`
  컬럼이 없는 DB를 만들고 행을 넣은 뒤 열면, 마이그레이션이 컬럼을 추가하고 조회 결과의
  `estimatorVersion`이 `'v1'`, `advertisedTokens`가 `null`이다.
- `round-trips a server context overhead`: `upsertServerContextOverheads` 후
  `allServerContextOverheads`가 같은 레코드를 돌려준다.
- `overwrites a server context overhead on rescan`: 같은 서버로 두 번 저장하면 행이 1개이고
  나중 값이 남는다.

**T2** (`packages/core/test/scanner/calibration.test.ts` 신규)

- `excludes outputSchema from the token count`: `outputSchema`만 다른 두 툴 정의의
  `advertisedTokens`가 같다.
- `counts the fully qualified tool name`: 서버 이름이 긴 쪽의 `advertisedTokens`가 더 크다.
- `calibrated tokens are the advertised tokens times the harness factor`:
  `definitionTokens === Math.round(advertisedTokens * 1.608)`.
- `stores zero instructions tokens when the server publishes none`: `getInstructions()`가
  `undefined`인 스텁 서버에서 `instructionsTokens`가 0이고 `instructionsSha256`이 `null`이다.
- `matches the measured day-01 weights within 10 percent on average`:
  `packages/core/test/fixtures/calibration/day-01.json`의 10개 서버에 대해
  `mean(|calibratedTokens − measuredTokens| / measuredTokens) < 0.10`.
  픽스처의 `meanV2ErrorRate`(0.0743)와도 소수 3자리까지 같다.
- `the uncalibrated estimator would have failed the same bar`: 같은 픽스처의
