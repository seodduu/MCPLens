## 무엇이 문제였나

Claude Code는 zero-call 툴도 트리에 뜬다. 로드 이벤트에 서버 identity가 붙어
`loadedSessionCount > 0`으로 표시 필터를 통과하기 때문이다. Codex는 통과하지 못했고
원인이 둘이었다.

**B. 다중 정의 출력을 통째로 버렸다.** `classifySearchOutput`이 출력 배열의 원소가 정확히
1개가 아니면 `generic`으로 떨어뜨렸다. 실 로그 359개 세션 전수 조사 결과 실제 검색 60건 중
48건(80%)이 부분일치 검색(`x.name.includes(...)`)이었고, 그 출력은 대부분 정의 여러 개짜리
배열이었다. 복구 가능한 배열 형태가 53건 중 35건이었다.

**A. 이름을 얻어도 서버 귀속이 null로 굳었다.** 귀속을 수집 시점에 하고 있어서 관측이 스캔보다
먼저 들어오면 후보가 0건이라 null로 저장되고 소급 보정 경로가 없었다. 실 DB가 정확히 그
상태였다(`js_reset` 검색 관측 08-03 19:07, `node_repl` 정의 스캔 08-04 11:57). 로그 파일은
`file_cursors`로 재읽기가 억제되므로 재수집으로도 회복되지 않았다.

## 이번에 확인한 사실 (기록용)

**훅으로는 코드모드 검색을 못 잡는다.** `packages/codex-plugin/hooks/hooks.json`의
`PreToolUse`/`PostToolUse` matcher가 `^mcp__(.+?)__(.+)$`라 실제 MCP 툴 호출만 잡는다. 코드모드
검색은 내장 `exec` 툴로 샌드박스 JS를 돌리는 것이고, 어느 툴이 로드됐는지는 스크립트 출력에만
남는다. 그 출력은 훅 페이로드가 아니라 로그의 `custom_tool_call_output`에 있다. 정의 로드
관측이 로그 전용인 구조적 이유다. 실 DB에서도 신규 3건이 전부 `source=log`로 기록됐다.

**로그 반영에 세션 종료가 필요하지 않다.** 4차 E2E는 세션을 끝내야 로그가 flush된다고 기록했으나,
이번에는 codex 세션을 종료하지 않은 상태에서 검색 3건이 그대로 수집됐다. codex가 rollout jsonl에
증분으로 쓰고 로그 워처가 실시간으로 읽는다. 4차의 관측은 일반 규칙이 아니라 그 케이스 한정이었다.

## 남은 위험

- 객체 래퍼 출력(`{"matches":[...]}`, 실측 6건)과 잘린 출력(`Warning: truncated output`, 6건)은
  계속 `generic`으로 버린다. 래퍼 키는 모델이 매번 다르게 짓고, 잘린 정의는 토큰 수를 신뢰할 수
  없다. 계획서 4장의 고정 결정이다.
- 회복 패스는 매 활성화마다 돈다. 후보가 0개 또는 2개 이상이라 영구히 회복되지 않는 세션은
  활성화마다 재구축된다. 실 DB 대상이 5건이라 실측 부담은 없었고 지연도 눈에 띄지 않았다.
- `upsertClientServers`는 `this.transaction(...)`으로 감싸여 있지 않다. 이제 이 메서드가
  `rebuildSession`까지 수행하므로 중간 실패 시 롤백 단위가 없다. 기존에도 `client_servers`
  DELETE와 INSERT가 같은 상황이라 이번 변경이 새로 만든 문제는 아니다. 별건으로 다루는 편이 낫다.
- `loadedTokens` 의미가 성공 경로에서 "출력 원문 전체"에서 "원소별 정의"로 바뀌었다. 다중 로드
  합계는 메타데이터 블록과 배열 구분자만큼 원문보다 작다. 의도된 변경이다.
