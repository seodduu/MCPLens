## 합격 기준 2 (범위 축소): Codex 수집 건강도 회복과 collection-health-unsafe 해소 — PASS

### 원래 기준이 통과 불가능했던 이유 (preflight에서 발견, 이번 회차 새 관측)

Codex `tool_loads` 전 건이 `server_name` 빈 값 + `(code-mode-search)` 의사 툴로만 기록되어
`loadedSessionCount`가 항상 0이다. 트리 노출(`matrixTree.ts:142` → `extension.ts:453`)과 액션 후보 자격
(`engine.ts:152-155`)이 모두 `callCount > 0 || loadedSessionCount > 0`을 요구하므로, **호출된 적 없는 codex
툴은 절대 트리에 나타나지 않는다.** `lenstest2`를 신규 등록해 hook 호출을 만들어도(이번 회차에 실제로
등록·호출까지 해봄) 신규 zero-call 툴 10개는 전부 `VISIBLE=false`로 남았다(preflight가 DB 사본으로
시뮬레이션, 이번 회차 실기기 등록 후에도 동일 확인). **이 항목은 이번 회차 범위 밖의 코드 변경 없이는
어떤 방법으로도 통과할 수 없다.** 결함 후보로 별도 기록 권고(아래 "신규 발견" 참조).

### 사용자 승인 하 대체 기준: 건강도 회복 + 호출된 codex 툴에서 collection-health-unsafe 사유 소멸

## 신규 발견: Codex zero-call 액션 후보 구조적 노출 불가 (제품 결함 후보)

`engine.ts:152-155`와 `matrixTree.ts:142`가 codex 툴의 트리 노출·액션 후보 자격을
`callCount > 0 || loadedSessionCount > 0`으로만 판정하는데, codex의 `tool_loads`가 전부
`server_name` 빈 값 + `(code-mode-search)`로만 기록되어 `loadedSessionCount`가 항상 0이 된다.
결과적으로 **codex에서는 한 번도 호출되지 않은 툴에 대해 전역 비활성화 액션을 제안할 방법이 없다**
(Claude·gemini-cli는 이 문제가 없다 — 두 클라이언트는 로드 이벤트에 실제 identity가 붙는다).
이건 이번 태스크의 코드 변경 범위 밖이므로 고치지 않았고, 별도 결함 티켓/계획으로 다뤄야 한다.
