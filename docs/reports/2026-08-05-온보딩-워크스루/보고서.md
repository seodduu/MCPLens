유닛테스트로는 잡을 수 없는 종류다.

## 발견 1 — 네이티브 자동 오픈은 신뢰할 수 없다

VSIX를 설치해도 워크스루 탭이 열리지 않았다. VS Code 본체 소스를 읽어 조건을 확인했다
(`gettingStartedService.ts`).

```ts
const isNewlyInstalled = !this.metadata.get(categoryID);
...
if (hadLastFoucs && sectionToOpen &&
    this.configurationService.getValue('workbench.welcomePage.walkthroughs.openOnInstall') && ...)
```

조건이 다섯이다. 창 포커스 이력, 세션 내 설치 기록, `walkthroughMetadata`에 없을 것,
설정값, startupEditor. 확장이 제어할 수 있는 것이 하나도 없다.

결정적인 것은 세 번째다. `categoryID`가 한 번 기록되면 확장을 삭제해도 남는다.
실제로 이 머신의 `state.vscdb`에 다음이 남아 있었고, 그 뒤로는 몇 번을 재설치해도 뜨지 않았다.

```json
["seodduu.mcp-context-lens#mcpLens.setup",
 {"firstSeen":1785869837747,
  "stepIDs":["…#scan","…#hooks","…#analyze","…#actions"],"manaullyOpened":true}]
```

**조치**: 확장이 직접 연다. 첫 활성화에서 `globalState` 플래그를 확인하고
`workbench.action.openWalkthrough`를 호출한다 (`firstRun.ts`, 커밋 `5c948b5`).

**재검증**: 확장 삭제 + `globalState` 플래그 삭제 후, **네이티브 경로가 죽어 있는 상태**
(`walkthroughMetadata`에 항목이 남은 채)에서 CLI로 설치했다. 워크스루가 열렸다.
즉 우리 코드가 연 것이 확실하다.

부수 효과로 스텝 id 형식이 실증됐다. 위 `stepIDs`가 `setupContextKeys.ts`의 상수와 정확히
일치한다. 코드가 자기 자신하고만 대조하던 값이었다.

## 발견 2 — `onSettingChanged`는 발화 전에 소진된다

스텝 4를 `onSettingChanged:mcplens.dependencyAnalysis.rollout`으로 두었는데, 설정을
`claude`로 바꿔도 체크가 켜지지 않았다.

```ts
progressByEvent(event: string): void {
  if (this.sessionEvents.has(event)) { return; }
  this.sessionEvents.add(event);
  this.completionListeners.get(event)?.forEach(id => this.progressStep(id));
}
```

`sessionEvents`는 리스너 등록 이전 발화도 삼킨다. 확장의 configuration 기여가 등록될 때
`onDidChangeConfiguration`이 그 키를 담아 발화하므로, 사용자가 값을 바꾸기 전에 이벤트가
소진된다.

**조치**: 스텝 4도 `onContext:mcpLens.globalActionsReady`로 통일 (커밋 `b86e2cf`).

**재검증**: `claude`로 바꾸면 체크가 켜지고, `shadow`로 되돌리면 다시 꺼진다. 둘 다 확인.

## 발견 3 — 해제하면 다시 켤 수단이 없어진다

Codex 신뢰를 풀어 스텝 2 체크가 꺼진 뒤(의도한 동작), `/hooks`에서 승인해 수집이 정상으로
돌아왔는데 체크가 돌아오지 않았다. Collection Status는 `codex: Healthy`인데 워크스루만
꺼진 채 남았다.

원인은 발견 2와 같은 중복 제거다. `onContext:<키>`는 세션당 1회만 유효하다. 우리가
`welcome.markStepIncomplete`로 끄면 그 이벤트는 이미 소진돼 있어 다시 켜줄 주체가 없다.
**해제 기능을 넣는 순간 점등도 우리 책임이 된다.**

**조치**: 거짓→참 전이에서 `welcome.markStepComplete`를 호출한다 (커밋 `b11202b`).
`markStepIncomplete`와 대칭이며 실패는 동일하게 삼킨다.

**재검증**: 동일 세션 안에서 신뢰 해제 → 체크 꺼짐 → 승인 → **리로드 없이** 체크 재점등.
리로드를 끼우지 않은 것이 핵심이다. 리로드하면 세션이 갈려 이 결함이 숨는다.

## 통과 항목 상세

**스텝 2 (`needs-approval`).** `~/.codex/config.toml`의 mcp-lens 훅 4개 섹션에서
`trusted_hash`만 제거해 승인 대기 상태를 만들었다(oh-my-codex 7개는 보존). 결과는
스텝 2 체크 꺼짐, Collection Status `codex: Awaiting approval · codex consent needed`.
설정 파일 감시가 돌아 **리로드 없이** 반영됐다. `onCommand` 기반이었다면 체크가 켜진 채
수집 0건인 상태가 됐을 지점이다.

**`Install hooks` 승인 대기 안내.** 같은 상태에서 버튼을 눌렀다.

```
MCP Lens: approval for codex is pending. Open codex's /hooks and approve
the MCP Lens hooks to continue.
```

최종 리뷰에서 지적된 세 번째 Important의 수정 결과다. 수정 전에는 설치 대상이 0개라
`hooks are already installed.`를 띄워, 사용자가 아무 변화도 없는 버튼을 반복해 누르는
상태였다.

**Setup Status 뷰.** 세 그룹이 실제 값으로 그려진다.
MCP authentication은 서버 9개(`authenticated` 6, `ignored` 3),
Dependency analysis는 `Provider claude · consented`와 분석된 서버 6개,
Global actions는 `locked (shadow)`.
인증 그룹(9)과 분석 그룹(6)의 개수 차이는 정의가 있는 서버만 분석 대상이라는 사양대로다.
`authIgnore`에 넣은 서버가 `ignored`로 표시되고 클릭 동작이 없는 것도 확인했다.

**미노출 상태.** `login required`·`never scanned`·`scan failed` 행은 이 환경에서 재현되지
않아 눈으로 못 봤다. 유닛테스트로만 검증된 상태로 남는다.

## 남은 것

- `mcplens.dependencyAnalysis.rollout`이 현재 `shadow`다. 검증 중 `claude`로 바꿨다가 되돌렸다.
- `packages/cli`의 scan 경로는 `server_scan_status`를 기록하지 않는다. 이 브랜치 범위 밖이라
  별건으로 남긴다. CLI로만 스캔한 사용자는 Setup Status가 `run a scan`으로 보인다.
- 최종 리뷰에서 park된 항목 1건(생성 가드 커버 테스트 무효)은 그대로다.
