## 0. 이 로드맵이 나온 배경 — 실측으로 확인한 사실들

2026-08-01~02 사이 실기기 DB(`~/.mcplens/lens.db`)와 원본 로그를 직접 검증하며
아래 사실을 확인했다. 모든 논의의 출발점이므로 숫자째로 기록한다.

| 사실 | 실측값 | 의미 |
|---|---|---|
| notion 서버 정의 총량 | 20툴 21,301tok, 실호출 9회 | "비용 큰데 사용 적음"의 전형 |
| 검색 오염 | 1세션에서 notion 툴 12개 로드, 실사용 2개. `notion-query-meeting-notes` 3,374tok가 호출 0회로 상주 | 지연 로딩의 검색이 관련 툴 정의를 묶음으로 끌어옴 |
| 지연 로딩 검색 비용 | Codex `(code-mode-search)` 1회당 14~10,813tok, 누계 38,766tok | 지연 로딩은 무료가 아니라 후불 |
| 호스트 주입 서버 | claude-in-chrome 860회 호출, 정의 토큰 0행(미측정) | 설정 파일에 없는 서버는 스캔 불가(구조적) |
| 응답 토큰 정확성 | `read_network_requests` 9건을 원본 로그에서 재계산, 전부 일치 | 수집 파이프라인 자체는 정확 |
| 단일 호출 왜곡 | 위 9건 중 1건이 24,675tok(전체의 93%, base64 덩어리) | 합계 표시가 "상시 비싼 툴"과 "한 번 물린 툴"을 구분 못 함 |
| 토크나이저 한계 | `o200k_base`(OpenAI 인코딩) 사용 | Claude 실토크나이저와 다름. 근사치임을 항상 명시 |

핵심 발견 두 가지:

1. **지연 로딩 시대에도 낭비는 실재한다.** 다만 형태가 바뀌었다.
   전량 선불(선로드)의 낭비가 아니라 검색 오염(로드됐으나 호출 0회)이 주범이다.
2. **삭제 기능에는 우리가 아직 답하지 못한 안전성 문제가 있다.** (3장)

## 1. 버전 로드맵 한 줄 요약

| 버전 | 정체성 | 사용자에게 주는 것 |
|---|---|---|
| v1 | **관찰.** 수집 도구 그 이상도 이하도 아님 | "이게 낭비구나"를 실측으로 아는 것 |
| v2 | **판단 보조 + 고지된 가역 조치** | 지워도 안전한 툴을 골라주고, 알고 지우게 하고, 잘못 지우면 알려주는 것 |
| v3 | **원클릭 자동화(압축)** | 버튼 하나로 안전한 범위만 정리, 언제든 통째 롤백 |

단계 논리: 관찰 → 조언 → 자동화. 각 단계는 앞 단계의 신뢰 위에서만 성립한다.
v1의 측정이 정확하다고 믿어야 v2의 권고를 듣고, v2의 권고가 맞았어야 v3의 버튼을 누른다.

## 2. 관통 원칙 (버전 무관, 위반 금지)

1. **비가역 조작은 없다.** 모든 조치는 관측되고 되돌려진다.
   사용자가 필요하다고 느끼는 순간 언제든 복구 가능해야 한다.
   백업 없는 삭제 경로는 만들지 않는다.
   (근거: 기존 코드도 이미 이 원칙이다. deny는 규칙 한 줄 추가/제거,
   서버 비활성은 스태시 파일로 원형 그대로 이동 후 무손실 복원,
   쓰기 전 `.mcplens.bak` 백업 + tmp/rename.)
2. **측정 정직성.** 미측정은 0으로 뭉개지 않고 미측정이라 표시한다.
   실측·하한 추정·전량 가정을 라벨로 구분한다. 토크나이저 근사임을 숨기지 않는다.
3. **fail-open.** CLI가 없으면 해당 기능만 조용히 꺼지고 나머지는 돈다.
   파싱 실패는 throw 대신 계수. 읽기 실패면 쓰지 않는다.
4. **비용 투명성.** 확장이 사용자 계정으로 LLM 추론을 돌릴 때는 반드시 사전 고지한다.
   컨텍스트 아끼자는 도구가 몰래 토큰을 쓰면 존재 이유가 무너진다.

## 3. 문제 인식의 기록 — 왜 v1에서 삭제를 빼기로 했나

### 3-1. A-B 의존 시나리오 (2026-08-02 논의)

사용자가 툴 A를 낭비로 판단해 삭제. 그런데 B가 A와 결합돼 있어
A가 필요한 상황이 옴. 모델은 A가 지워진 걸 모르고(deny는 클라이언트 쪽 필터,
서버는 여전히 A를 목록에 줌) A를 찾다가 실패하고 우회를 시도하며 토큰을 태움.
**토큰 아끼려던 도구가 토큰을 더 쓰게 만드는 역전.**

메커니즘 보정 (논의에서 정리된 것):

- MCP에서 툴이 툴을 직접 부르는 일은 없다. 호출 주체는 항상 모델.
  실제 위험은 ①워크플로 결합(A의 결과가 있어야 B가 의미 있음.
  navigate 없이 read_page가 소용없는 식) ②정의 텍스트 상호 참조
  ("먼저 X를 호출하라"가 설명문에 적힌 서버가 실재함).
- 지연 로딩에서 실패한 검색도 유료다: 검색할 때마다 후보 툴들의 정의가
  통째로 로드되어 세션 끝까지 상주(실측 1회 최대 10,813tok).
  "찾다가 폭주"의 비용 실체가 이것.
- 다만 폭주는 유한하다(모델은 몇 번 실패하면 포기·우회).
  사고당 수천~수만 tok에서 막힘.
- **산수만 보면 제거가 이득일 때가 많다**(3,374tok × 매 세션 vs 사고당 1만tok).
  진짜 문제는 토큰이 아니라 **실패의 종류**: 작업 자체가 깨지는 것은
  토큰 낭비와 질적으로 다른 급의 손해. 손해의 비대칭이 핵심.

### 3-2. 엣지 케이스는 무한해 보이지만 뿌리는 셋

1. **시간적 사각**: 관찰 창(기본 30일) 밖의 필요.
   월말 정산 툴, 장애 때만 쓰는 복구 툴. 평소 0회라 remove 후보로 뜨는데
   필요한 순간은 관찰 밖. 복구용 툴은 "가장 필요한 순간에 없는" 최악 형태.
2. **구조적 사각**: 툴 간 의존을 엔진이 모름 (3-1).
3. **범위 불일치**: deny는 `~/.claude/settings.json`, 즉 사용자 전역.
   프로젝트 X에서 안 쓴다고 지우면 Y에서도 사라짐.

→ 수백 사례를 패치하지 말고 원인 셋을 다룬다. v2 설계가 이 셋에 대한 응답이다.

### 3-3. 현 설계가 이미 막고 있는 부분 (과대평가 금지)

- remove 권고는 호출 0회 툴에만 나간다. 실제로 쓰이는 세트의 조각을
  지우라고 권하는 일은 데이터상 드물다.
- 확신 낮으면 "후보"로 렌더링(판정 강등 없이 표면에서 완화).
- 위험이 남는 정확한 케이스: A·B 둘 다 관찰 기간 미사용, 사용자가 A만 삭제,
  나중에 B가 필요해짐.

## 4. v1 — 관찰 전용으로 재정의

**결정: v1은 모니터링에만 목적이 있다. 삭제도 복구도 없다.**
"아 이게 낭비구나, 이렇게 많이 쓰는구나"에서 끝나는 것이 v1의 완성이다.

- 현재 코드에 이미 있는 remove/add(툴 deny 토글, 서버 비활성)는
  v1 표면에서 **뺀다**(코드 삭제인지 숨김인지는 결정 필요, 7장).
  근거: 의존성 문제의 답이 없는 상태로 삭제 버튼을 내보내는 것보다
  "우리는 재기만 한다, 정확하게"로 시작하는 쪽이 신뢰 서사에 맞다.
- v1에서 다듬을 것(측정 정직성 강화):
  - 미측정 사유 분리 표시: "호스트 내장이라 스캔 불가"(구조적) vs
    "인증하면 측정됨"(github·figma류). 사용자가 취할 행동이 다르다.
  - 합계 왜곡 보정: 서버·툴 행에 최대값(또는 중앙값) 병기.
    `9회 · 26,608tok (최대 24,675)` 형태. 데이터는 이미 행 단위로 있음.
  - (선택) `(code-mode-search)` 검색 비용을 리포트에 노출.
    server_name이 비어 서버 집계에 안 붙는 상태. 구조적 한계가 아니라 미연결.

## 5. v2 — LLM 독립성 판정 + 고지된 가역 삭제

### 5-1. 사용자 원안 (2026-08-02)

- VS Code 확장이 CLI(claude든 codex든 무관)를 부른다.
- 가장 저렴하고 빠른 모델에게 "이 툴을 삭제해도 다른 툴에 절대 영향이
  안 가는 독립적인 툴"을 골라내게 해서 표시한다.
  이떄 CLI에게 넘기는 프롬프트는 무조건 영어로 넘긴다.
- 사용자가 낭비라고 판단하면 그 독립 툴을 삭제할 수 있다.
- 삭제 시점에 이 툴이 뭘 하는 물건인지 한 줄로 알려준다.
  "이 툴을 지우면 이 기능을 더 못 쓴다. 이 기능을 LLM에게 맨손으로 시키면
  상당한 리스크가 동반된다" 수준의 경고 포함. 단편적 기능이라도 알고 지우게 한다.

### 5-2. 채택 + 보정 세 가지

원안의 뼈대는 채택. 아래 세 가지를 보정한다.

**보정 1: LLM 단독 판정 금지, 하이브리드로.**
결정적으로 잡히는 신호를 먼저 쓰고 LLM은 남는 것만 맡는다.

| 계층 | 신호 | 방법 | LLM 필요 |
|---|---|---|---|
| 1 | 정의 텍스트 상호 참조 | 스캐너가 가진 정의 원문에서 형제 툴 이름 grep | 불필요 |
| 2 | 연쇄 호출 통계 | `tool_calls` 시각 기반, 같은 세션에서 붙어 다니는 쌍 | 불필요 |
| 3 | 의미적 결합 | "navigate 없이 read_page 무의미" 같은 판단 | 필요 |

이유: LLM 판정은 비결정적이고 환각 위험이 있다. 1·2층이 하한선을 보장하면
LLM이 틀려도 최악을 면한다. 비용도 준다.

**보정 2: 독립성은 방향이 있다.**
삭제 안전성에 필요한 건 "A가 남에게 의존하나"가 아니라 **"남이 A에 의존하나"**다.
정의: **진입 차수 0** = 어떤 툴의 설명문도 A를 참조하지 않고,
어떤 관측된 워크플로에서도 A가 선행 단계가 아니면 독립.
LLM 프롬프트도 이걸로 명확해진다: "이 정의 목록에서 서로를 전제하는 쌍을 찾아라."

**보정 3: 판정은 캐시한다.**
정의는 거의 안 바뀐다. 정의 해시를 키로 판정을 저장하면 서버당 LLM 호출은
사실상 1회. 기능 요약·경고 문구도 같이 생성해 같이 캐시.

### 5-3. 후회 감지 (v2의 완성 조건)

사전 경고만으로는 시간적 사각(3-2의 1번)을 못 막는다. 지우기 전 완벽한 예측은
불가능하므로, **지운 뒤 틀렸음을 자동으로 아는 것**으로 보완한다.

- 우리는 수집 도구다. deny된 툴을 모델이 찾으려던 흔적(거부된 호출 시도,
  실패한 검색 뒤의 우회 패턴)은 로그·훅에 남는다.
- 이를 감지하면: "A를 지운 뒤 3세션에서 A가 필요했던 정황. 복구 권장."
- 복구는 어차피 클릭 한 번의 가역 조작(2장 원칙 1).

사전 경고(고지된 삭제) + 사후 회수(후회 감지) = 양방향 안전망. 이 둘이 갖춰져야
v2가 "권고를 실험으로 취급하는" 도구가 된다.

### 5-4. 기술 기반 — 이미 검증된 것

- **확장의 CLI 호출은 신규 관문이 아니다.** 훅 설치가 이미 `claude plugin ...`을
  자식 프로세스로 실행 중. `claudeCli.ts`가 GUI PATH 문제(알려진 설치 위치 우선 탐색),
  대화형 프롬프트 무한 대기(stdin 차단 + 120초 타임아웃, gemini-cli 0.51.0 실측),
  Windows `.cmd` spawn(CVE-2024-27980 대응)까지 해결해 둠. 테스트 존재.
- v2 추가분은 헤드리스 추론 호출:
  `claude -p "<프롬프트>" --model haiku --output-format json` (Codex는 `codex exec`).
- 유의: ①추론은 설치 명령보다 오래 걸릴 수 있음. 타임아웃 상향 + 백그라운드 실행
  + 캐시 전제로 UI 비대기 설계 ②비용이 사용자 계정으로 나가므로 첫 실행 시 고지
  (2장 원칙 4) ③CLI 부재 시 v2 판정만 꺼지고 v1은 그대로 (2장 원칙 3).

### 5-5. 가치 평가의 기록 (2026-08-02 시점 판단)

- **실용성 6/10.** 문제는 실재하나 지연 로딩 보편화로 절대 크기가 줄었다.
  절약 폭이 가장 큰 대상은 선로드 클라이언트와 검색 오염 정리.
  삭제 자체는 손으로도 되므로 실용 가치의 몸통은 폐루프
  (실측 → 권고 → 조치 → 후회 감지 → 복구)다. 이건 손으로 못 한다.
  마케팅에서 "수만 토큰 절약"은 지연 로딩 사용자에게 과장이 됨. 주의.
- **화제성 7~8/10.** 다만 화제성의 몸통은 v2 기능이 아니라 **v1의 실측 데이터**다
  (0장의 숫자들). 공개 순서를 지켜라: v1을 숫자와 함께 먼저 공개하고
  그 반응 위에 v2를 올린다. 순서를 바꾸면 안 된다.
- **포트폴리오 9/10.** 측정 규율, 시스템 설계(멀티소스 정준화, writer lease,
  멱등 inbox), 그리고 "자기 기능의 실패 모드를 스스로 발견하고 재설계한 서사"
  (삭제 기능을 만들었다가 의존성 문제를 찾아 v1에서 빼고 v2에서 안전망과 함께
  재도입). 이 서사가 기능 목록보다 세다.
- **플랫폼 리스크**: 클라이언트가 네이티브 컨텍스트 회계를 내장하면 실용성·화제성은
  깎이지만 포트폴리오 가치는 안 깎인다("플랫폼보다 먼저 만들었다"는 문제 선정의 증거).
- 따라서 v2 개발 중 판단 기준은 "사용자가 늘까"보다
  **"이 설계 결정을 남에게 설명할 수 있나"**에 둔다.

## 6. v3 — 원클릭 압축

### 6-1. 사용자 원안

"이 MCP를 압축시켜줘" 버튼을 누르면 낭비라고 판단되는 것들을 전부 압축.
최대한 독립적인 것 위주로. 독립적인 것이 생각보다 없다면
낭비로 보이는 것들을 그냥 삭제.

### 6-2. 기각 조항과 이유 (중요 — 잊지 말 것)

**"독립적인 것이 없으면 낭비로 보이는 것을 그냥 삭제"는 기각.**

이 조항은 3장의 실패 시나리오를 자동화 버튼 뒤에 숨겨 대량 실행하는 것이다.
독립 판정이 안 된 툴을 지우는 순간 A-B 문제가 확률이 아니라 설계로 보장된다.
v2에서 쌓은 "고지된 삭제" 원칙을 v3가 스스로 부순다.

### 6-3. 채택안: 계층형 압축

버튼 한 방의 범위를 계층으로 제한한다.

| 계층 | 대상 | 동작 |
|---|---|---|
| 1 | 독립 + 미사용 | 자동 deny. **여기까지만 무확인 자동화** |
| 2 | 의존 세트인데 세트 전체가 미사용 | "이 3개는 세트다, 같이 지울까?" 세트 단위로 질문 |
| 3 | 의존인데 일부만 사용 | 건드리지 않음. 목록만 표시 |

필수 동반 장치:

- **압축 직전 스냅샷 + 원클릭 롤백("압축 해제" 버튼).**
  스태시 메커니즘이 이미 무손실 왕복을 하므로 기존 구조의 연장선.
- 후회 감지(5-3)가 압축 결과를 감시하고 자동으로 롤백을 제안.

### 6-4. v3의 대안 해석 — 정의 다이어트 (후보로 병기)

"압축"의 다른 해석: 지우는 게 아니라 **정의 자체를 줄이는 것**.
프록시가 `tools/list` 응답을 지나가며 장황한 설명문을 요약본으로 교체하면
툴은 전부 살아 있는데 상주 비용만 준다. notion 툴당 평균 1,065tok의 상당 부분이
문서 수준 설명문이다. lens-proxy 인프라가 로드맵에 이미 있어 기술 토대가 겹친다.

- 장점: 삭제가 없으므로 A-B 문제 자체가 없음. "압축"이라는 이름값에 더 맞음.
- 리스크: 요약된 설명으로 모델의 툴 선택 성능이 떨어질 수 있음. 검증 필요.
- 지위: 6-3과 배타적이지 않다. v3 범위 결정 시 함께 평가(7장).

## 8. 이 문서를 읽는 미래의 나에게

- 삭제 기능을 다시 넣고 싶어질 때: 3장을 먼저 읽어라. 문제는 삭제가 아니라
  **의존을 모르는 삭제**였다. 답은 기능 제거가 아니라
  "권고를 실험으로 취급하고 회수 루프를 붙이는 것"이었다.
- v3를 서두르고 싶어질 때: 6-2를 읽어라. "독립 아니면 그냥 삭제"를
  기각한 이유가 거기 있다. 편의가 원칙을 이기게 두지 마라.
- 어떤 조치 기능을 설계하든 2장 원칙 1로 돌아와라:
  **사용자가 필요하다고 느끼는 순간 언제든 복구할 수 있어야 한다.**
  이 문장이 이 로드맵 전체의 헌법이다.
