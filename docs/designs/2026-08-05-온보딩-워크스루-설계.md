# 온보딩 워크스루와 Setup Status 뷰 설계

작성 2026-08-05. 대상 패키지 `packages/extension`, `packages/core`(테이블 1개 추가).

## 문제

확장을 설치한 사용자가 Lens의 전 기능에 도달하려면 네 가지를 해야 한다. 서버 스캔, 훅 설치,
의존성 분석, 전역 조치 활성화. 지금은 이걸 알림 팝업으로만 안내한다. 팝업은 순서를 못 보여주고,
놓치면 다시 볼 방법이 없고, 지금 어디까지 왔는지도 알 수 없다.

특히 순서가 문제다. 의존성 분석(`analyzeUncachedServers`)은 저장소에 있는 툴 정의를 입력으로 쓰고,
정의는 스캔이 채운다. 스캔 없이 분석을 먼저 돌리면 빈손으로 끝난다. 사용자가 이 의존 관계를
알 방법이 지금은 없다.

## 해결

두 개를 만든다.

1. **VS Code 네이티브 워크스루** (`contributes.walkthroughs`). 확장 신규 설치 시 자동으로 열리는
   "시작하기" 탭. 4스텝. 각 스텝의 완료 체크는 확장이 실제 상태를 판정해 켠다.
2. **Setup Status 뷰**. 사이드바 세 번째 트리뷰. 워크스루를 닫은 뒤에도 남는 상태판.

UI 문자열은 전부 영어로 쓴다. 기존 한국어 문자열도 이 작업에서 함께 영어로 바꾼다.
문서·주석·커밋 메시지는 계속 한국어다.

## 결정 기록

| 결정 | 대안 | 근거 |
|---|---|---|
| 네이티브 워크스루 | 커스텀 웹뷰 | 웹뷰 코드 0줄, 자동 오픈이 공짜. 대신 스텝 본문은 마크다운+이미지 1장으로 제한되므로 클라이언트별 상태표는 뷰가 맡는다 |
| 완료 판정은 `onContext` | `onCommand` | `onCommand`는 커맨드 실행 사실만 본다. Codex는 설치 커맨드가 성공해도 `needs-approval`로 남아(`installers/codex.ts:46`) 수집이 0건인데 체크가 켜지는 거짓 성공이 난다 |
| Setup Status에 훅 그룹 없음 | 훅 포함 | 훅 상태는 기존 Collection Status 뷰가 이미 그린다. 두 곳에 그리면 갱신 시점이 어긋날 때 서로 다른 말을 한다 |
| 전역 조치는 한 줄 | 클라이언트별 행 | 실제 상태가 워크스페이스 설정 하나(`mcplens.dependencyAnalysis.rollout`)다. 클라이언트별로 그리면 없는 상태를 지어내는 것이다 |
| 스캔 상태를 DB에 저장 | 세션 메모리 | 인증 필요 여부는 스캔이 서버를 띄워봐야 알 수 있고, 지금은 알림 한 번 뜨고 사라진다. 저장하지 않으면 VS Code 재시작 후 뷰가 빈칸이 된다 |

## 1. 워크스루

`packages/extension/package.json`의 `contributes.walkthroughs`에 항목 하나.
id `mcpLens.setup`, title `Get started with MCP Lens`.

| # | title | description(요약) | 버튼(커맨드) | completionEvents |
|---|---|---|---|---|
| 1 | `Scan your MCP servers` | 각 툴 정의가 프롬프트에서 먹는 토큰을 잰다. 서버를 잠깐 띄워 `tools/list`만 부른다. LLM 토큰을 쓰지 않고 설정 파일을 고치지 않는다 | `Scan now` → `mcp-lens.scanNow` | `onContext:mcpLens.scanReady` |
| 2 | `Turn on usage collection` | 클라이언트에 훅을 설치한다. 훅이 있어야 실제 호출 횟수가 쌓이고 정의 토큰과 대조할 수 있다 | `Install hooks` → `mcp-lens.installHooksAll` | `onContext:mcpLens.hooksReady` |
| 3 | `Analyze tool dependencies` | 툴 정의와 집계 사용량만 보내 어떤 툴이 무엇에 의존하는지 판정한다. 프롬프트·툴 입출력·소스코드는 보내지 않는다 | `Analyze` → `mcplens.analyzeDependencies` | `onContext:mcpLens.analysisReady` |
| 4 | `Enable global actions (optional)` | Lens가 클라이언트 설정을 직접 고쳐 툴을 꺼준다. 기본은 잠겨 있다 | `Open setting` → `mcp-lens.openRolloutSetting` | `onContext:mcpLens.globalActionsReady` |

스텝 2의 description에는 클라이언트별 후속 조치를 문장으로 적는다.
Codex는 `/hooks`에서 직접 신뢰 승인해야 하고(보안 게이트라 자동화 불가), Gemini는 CLI 재시작이
필요하며, 어느 쪽이든 **새 세션부터** 수집이 시작된다.

각 스텝 미디어는 `media/walkthrough/step-N.svg` 플레이스홀더로 둔다. 규격 800×450, 다크/라이트
공용 색만 사용.

### 컨텍스트 키

세 키를 확장이 켠다. 판정은 새로 만들지 않고 이미 도는 감지 경로에 얹는다. 워크스루 체크와
Setup Status 뷰가 같은 근거를 쓰게 하기 위해서다.

| 키 | 참 조건 | 켜는 위치 |
|---|---|---|
| `mcpLens.scanReady` | `store.allDefinitions().length > 0` | 스캔 완료 후, 그리고 activate 시 1회 |
| `mcpLens.hooksReady` | 감지된 클라이언트(`install !== 'client-missing'`)가 1개 이상이고, 그 전부가 `install === 'installed'` | `computeCollection()` 말미 |
| `mcpLens.analysisReady` | 동의가 `accepted`이고, 정의가 있는 서버 중 1개 이상에 `findDependencyAnalysis` 결과가 있다 | 분석 완료 후, 그리고 activate 시 1회 |
| `mcpLens.globalActionsReady` | `mcplens.dependencyAnalysis.rollout` 값이 `off`가 아니다 | `computeCollection()` 말미, 설정 변경 감시에서도 |

`needs-approval`은 `hooksReady`를 켜지 않는다. 이 한 줄이 이 설계의 핵심이다.

### `onSettingChanged`를 쓰지 않는 이유 (실기기 검증으로 확정)

스텝 4는 처음에 `onSettingChanged:mcplens.dependencyAnalysis.rollout`으로 두었다. 실기기에서
설정을 `claude`로 바꿔도 체크가 켜지지 않았다. 원인은 VS Code 본체의 이벤트 중복 제거다.

```ts
progressByEvent(event: string): void {
  if (this.sessionEvents.has(event)) { return; }
  this.sessionEvents.add(event);
  this.completionListeners.get(event)?.forEach(id => this.progressStep(id));
}
```

`sessionEvents`는 리스너 등록 이전에 발화한 이벤트도 삼킨다. 확장이 등록되면서 자기
configuration 기여가 등록되고 그때 `onDidChangeConfiguration`이 그 키를 담아 발화하므로,
사용자가 실제로 값을 바꾸기 전에 이미 이벤트가 소진된다. 그 뒤로는 몇 번을 바꿔도 첫 줄에서
반환한다.

따라서 네 스텝 모두 `onContext`로 통일한다. 부수 효과로 `off`로 되돌리면 체크가 풀린다
(기존 참→거짓 전이 해제 배선을 그대로 탄다).

### 신설 커맨드

| 커맨드 | 하는 일 |
|---|---|
| `mcp-lens.scanNow` | 현재 `autoScan.ts`의 스캔 경로를 사용자 요청으로 강제 실행한다. `mcpLens.autoScan` 설정이 `never`여도 실행한다(사용자가 명시적으로 눌렀으므로). 완료 후 `mcpLens.scanReady` 갱신 |
| `mcp-lens.installHooksAll` | 감지된 클라이언트 중 `not-installed`인 것 전부에 `installHooks`를 순차 실행. 결과를 한 번의 요약 알림으로 보고 |
| `mcp-lens.openRolloutSetting` | `workbench.action.openSettings`를 `mcplens.dependencyAnalysis.rollout`으로 연다 |

`mcp-lens.scanNow`와 `mcp-lens.installHooksAll`은 커맨드 팔레트에도 노출한다. 워크스루를
닫은 사용자가 다시 찾을 수 있어야 한다.

## 2. Setup Status 뷰

`contributes.views.mcpLens`에 세 번째 항목. id `mcpLens.setupStatus`, name `Setup Status`
(워크스루 id `mcpLens.setup`과 겹치지 않게 별도 id를 쓴다).
기존 두 뷰 아래.

트리 최상위는 그룹 3개다. 훅은 없다.

### 그룹 A — `MCP authentication`

서버당 한 줄. 서버 목록은 `configSources`/`collectAllSpecs`가 주는 설정상의 서버 전체다.

| 상태 | description | 아이콘 | 클릭 |
|---|---|---|---|
| `authenticated` | `last scanned <상대시각>` | `pass` / charts.green | 없음 |
| `login required` | `sign in to scan` | `warning` / charts.orange | `authenticateServer` 실행 |
| `never scanned` | `run a scan` | `circle-outline` / 기본 | `mcp-lens.scanNow` |
| `scan failed` | `<error_code>` | `error` / charts.red | `mcp-lens.scanNow` |
| `unsupported` | `not supported by Lens` | `circle-slash` / 기본 | 없음 |

`unsupported`는 `mcpLens.unsupportedServers` 설정에 있는 서버(DCR 거부 등)다.
`mcpLens.authIgnore`에 있는 서버는 `login required`를 `ignored`로 바꿔 표시하고 클릭 동작을 없앤다.
사용자가 영구 무시를 택한 것을 뷰가 다시 재촉하면 안 된다.

### 그룹 B — `Dependency analysis`

첫 줄은 제공자다. label `Provider`, description은 상태에 따라
`claude · consented` / `codex · consented` / `not selected` / `consent required`.
클릭하면 `mcplens.analyzeDependencies`(동의 모달까지 기존 경로 그대로).

그 아래 정의가 있는 서버마다 한 줄. `analyzed` / `not analyzed`.
`analyzed` 줄을 클릭하면 `mcplens.openAnalysisDetails`, `not analyzed`는 `mcplens.reanalyzeServer`.

### 그룹 C — `Global actions`

한 줄. `mcplens.dependencyAnalysis.rollout` 값에 따라
`off` → label `Global actions`, description `locked`, 아이콘 `lock`.
그 외 → description `enabled (<값>)`, 아이콘 `unlock`.
클릭하면 `mcp-lens.openRolloutSetting`.

description에 툴별 자격 검사가 별도로 있다는 사실은 넣지 않는다. 잠금 해제와 자격은 다른 층이고,
여기서 섞으면 "열었는데 왜 회색이냐"가 다시 생긴다. 자격 사유는 기존 매트릭스 뷰의 툴 행 툴팁이 맡는다.

## 3. 스캔 상태 저장 (core)

`packages/core/src/store/schema.sql`에 테이블 하나를 추가한다. 이 파일은 공유 계약이므로
이 태스크가 단독 소유자로 잡는다.

```sql
CREATE TABLE IF NOT EXISTS server_scan_status (
  server_name TEXT PRIMARY KEY,
  status      TEXT NOT NULL,
  scanned_at  TEXT NOT NULL,
  error_code  TEXT
);
```

`status`는 `'ok' | 'auth-required' | 'failed'` 셋뿐이다. `never scanned`는 행의 부재로 표현한다.
값을 하나 더 만들면 "행이 없음"과 "값이 never임"이 동시에 존재해 판정이 갈린다.

기존 DB에도 이 테이블은 그냥 생긴다. `LensStore.open`이 열 때마다 `db.exec(SCHEMA)`를 돌리고
DDL이 `IF NOT EXISTS`이기 때문이다(`store.ts:62-64`). `migrate()`에 손댈 필요가 없고,
번호 매기는 마이그레이션 체계가 없으므로 번호 역전 위험도 없다.

공개 API 두 개를 `LensStore`에 더한다.

```ts
recordServerScanStatus(
  serverName: string,
  status: 'ok' | 'auth-required' | 'failed',
  scannedAt: string,
  errorCode?: string,
): void;

serverScanStatuses(): ReadonlyMap<string, {
  status: 'ok' | 'auth-required' | 'failed';
  scannedAt: string;
  errorCode?: string;
}>;
```

`recordServerScanStatus`는 `server_name` 기준 upsert다. 기록 시각은 호출자가 넘긴다
(`Date.now()`를 저장소 안에서 부르지 않는다. 테스트가 시각을 고정할 수 있어야 한다).

`autoScan.ts`의 `runScan`이 서버마다 이걸 호출한다. 판정 규칙은 지금 코드가 이미 쓰는 것과 같다.
`scanServer`가 던진 메시지에 `auth-required` 또는 `token-expired`가 들어 있으면 `'auth-required'`,
그 외 예외는 `'failed'`, 정상 종료는 `'ok'`.

## 4. 영어화

이 작업으로 확장의 사용자 노출 문자열을 전부 영어로 바꾼다. 새 화면만 영어로 하면 한 사이드바에
두 언어가 섞인다.

대상은 `package.json`의 뷰·커맨드 제목(`비용×사용 매트릭스` → `Cost × Usage Matrix`,

그리고 `packages/extension/src` 전체의 `showInformationMessage`/`showWarningMessage`/
`showErrorMessage`/`setStatusBarMessage` 인자와 `hookStatus.ts`의 표시 문구다.

대상이 아닌 것: 코드 주석, 커밋 메시지, `docs/` 문서, 테스트 이름.

## 자동 오픈 (실기기 검증으로 확정)

VS Code 네이티브 자동 오픈은 신뢰할 수 없다. 본체 조건이 다섯 개인데
(창 포커스 이력, `sessionInstalledExtensions` 등록, `walkthroughMetadata`에 없을 것,
`openOnInstall` 설정, startupEditor) 무엇도 확장이 제어하지 못하고, 한 번이라도
등록되면 `walkthroughMetadata`에 categoryID가 영구 기록되어 그 머신에서는 다시 뜨지
않는다. 실기기에서 CLI 설치 1회로 이 상태가 됐고 이후 UI 재설치로도 뜨지 않았다.

따라서 확장이 직접 연다. 첫 활성화에서 1회성 globalState 플래그를 확인하고
`workbench.action.openWalkthrough`를 호출한다.

```ts
const WALKTHROUGH_OPENED_KEY = 'mcpLens.walkthroughOpened';

async function openWalkthroughOnce(ctx: vscode.ExtensionContext): Promise<void> {
  if (ctx.globalState.get<boolean>(WALKTHROUGH_OPENED_KEY) === true) return;
  await ctx.globalState.update(WALKTHROUGH_OPENED_KEY, true);
  // 실패해도 확장 활성화를 막지 않는다 — 진실은 Setup Status 뷰다.
  void vscode.commands.executeCommand(
    'workbench.action.openWalkthrough', 'seodduu.mcp-context-lens#mcpLens.setup',
  ).then(undefined, () => {});
}
```

플래그를 먼저 기록하고 연다. 순서를 뒤집으면 open이 실패할 때마다 재시도해
매 활성화마다 탭이 뜨는 성가심이 생긴다. 한 번 시도했으면 끝이고, 놓친 사용자는
사이드바 Setup Status 뷰로 진입한다. VS Code 네이티브 자동 오픈과 겹쳐도
같은 워크스루 탭에 포커스만 이동하므로 무해하다.

## 체크 해제 (확정)

VS Code 본체 소스로 확인했다. `onContext` 완료는 **단방향이다.** 컨텍스트 변경 리스너가
표현식이 참일 때만 `progressByEvent`를 부르고, 거짓이 될 때 되돌리는 경로가 없다.
진행 상태는 memento에 영구 저장된다. 즉 훅을 제거해도 체크는 켜진 채 남는다.

```ts
// gettingStartedService.ts, initCompletionEventListeners()
this._register(this.contextService.onDidChangeContext(event => {
    if (event.affectsSome(this.stepCompletionContextKeys)) {
        this.stepCompletionContextKeyExpressions.forEach(expression => {
            if (event.affectsSome(new Set(expression.keys())) &&
                this.contextService.contextMatchesRules(expression)) {
                this.progressByEvent(`onContext:` + expression.serialize());
            }
        });
    }
}));
```

되돌리는 수단은 따로 있다. `welcome.markStepIncomplete` 커맨드가 `deprogressStep(id)`를 부르고,
그것이 진행 상태를 지우고 memento를 저장한다.

```ts
deprogressStep(id: string) {
    delete this.stepProgress[id];
    this.memento.saveMemento();
}
```

따라서 확장이 직접 끈다. 조건이 참에서 거짓으로 바뀌는 순간(예: 사용자가 훅을 제거하거나
Codex 신뢰가 풀려 `needs-approval`로 돌아갈 때) 해당 스텝 id로 이 커맨드를 부른다.

```ts
void vscode.commands.executeCommand(
  'welcome.markStepIncomplete',
  'seodduu.mcp-context-lens#mcpLens.setup#hooks',
);
```

스텝 id는 `${publisher}.${name}#${walkthroughId}#${stepId}` 형식이다
(`gettingStartedService.ts`: `extension.identifier.value + '#' + walkthrough.id + '#' + step.id`).
이 저장소 기준 접두사는 `seodduu.mcp-context-lens#mcpLens.setup#`이다.

배선 규칙은 이렇다. 컨텍스트 키를 갱신하는 자리에서 **이전 값과 비교**해 참→거짓 전이일 때만
`markStepIncomplete`를 부른다. 매번 부르면 사용자가 스텝을 손으로 체크한 것도 지운다.

**켜는 방향도 우리가 부른다** (실기기 검증으로 확정). 처음에는 `onContext`에 맡겼는데,
해제한 뒤 조건이 다시 참이 되어도 체크가 돌아오지 않았다. 원인은 VS Code의 세션 단위
중복 제거다.

```ts
progressByEvent(event: string): void {
  if (this.sessionEvents.has(event)) { return; }
  ...
}
```

`onContext:<키>`는 한 세션에 한 번만 유효하다. 우리가 `markStepIncomplete`로 체크를 끄면
그 이벤트는 이미 소진된 상태라 다시 켜줄 주체가 없어진다. 실기기에서 Codex 신뢰를 풀었다가
승인해 복구했을 때, 수집은 정상으로 돌아왔는데 스텝 2 체크만 꺼진 채 남았다.

해제를 도입한 이상 점등도 우리 책임이다. 거짓→참 전이에서 `welcome.markStepComplete`를
부른다. 이 커맨드는 `progressStep(id)`를 직접 호출해 `sessionEvents` 중복 제거를 우회한다.
`markStepIncomplete`와 같은 내부 커맨드이므로 실패는 똑같이 삼킨다.

매니페스트의 `onContext` 완료 이벤트는 그대로 둔다. 첫 세션에서 이전 값이 없을 때
(전이가 성립하지 않을 때) 체크를 켜주는 것은 여전히 그쪽이다.

주의: `welcome.markStepIncomplete`는 확장 API 문서에 없는 내부 커맨드다. 버전이 올라가며
사라질 수 있으므로 호출을 `try/catch`로 감싸고 실패해도 나머지 동작에 영향을 주지 않는다.
실패 시의 진실은 Setup Status 뷰다. 이 사실을 스텝 2 본문에 한 줄 적는다
(`Setup Status in the sidebar always shows the live state.`).

테스트는 전이 판정 함수만 순수 함수로 검증한다(`setupContextKeys.test.ts`에 추가).
- `참에서 거짓으로 바뀌면 해제 대상 스텝 id를 돌려준다`
- `거짓에서 거짓이면 아무것도 돌려주지 않는다` ← 손으로 체크한 것을 지우지 않기 위한 회귀 테스트
- `거짓에서 참이면 아무것도 돌려주지 않는다`

실기기 확인 항목에 하나 추가한다. 훅을 제거한 뒤 워크스루 스텝 2의 체크가 실제로 꺼지는지 본다.
내부 커맨드에 기대는 유일한 지점이므로 픽스처로 대신하지 않는다.
